# ФСП Талант

**команда Дмитрия Конькова** · [стенд](https://89-124-65-102.sslip.io) · [репозиторий](https://github.com/KonkovDV/fsp-talent)

Живой стенд с демо-входами · 1875 ключей заданий проверены запуском · API-ключи и вебхуки для ATS · юридический пакет

> **Грейд подтверждён тестом, место в выдаче объяснено, контакты открыты только с согласия кандидата.** Работодатель приходит к кандидату с вакансией и вилкой, а не наоборот.

> **[Что мы даём сверх ТЗ](docs/BEYOND_TZ.md)** — психометрика, удостоверения W3C VC, безопасность, доступность, валидация, интеграции и правовой пакет.

ФСП Талант — отраслевая платформа подбора ИТ-специалистов с обратной механикой. Кандидат входит через ФСП ID или по почте, проходит опрос и адаптивный тест и получает категорию «специализация × грейд»: грейд подтверждает только тест, результаты соревнований ФСП стоят отдельной подтверждённой осью и могут только поднять кандидата внутри категории. Работодатель описывает потребность, видит рекомендованные категории и подборку, где у каждого места есть разложение балла и объяснение, и сам отправляет приглашение с вилкой «от–до». Имя и контакты открываются только после согласия кандидата. Мы сделали её на ЛЦТ-2026 по задаче Федерации спортивного программирования.

Если объяснять простыми словами для HR, то так. Из 100 смоделированных кандидатов, которые завысили себе грейд в анкете, тест не подтвердит около 93 (92,6 % на зерне 7, 92,3 % на отложенных зёрнах). Если просто верить анкете, не подтвердится ни один: 0 из 100. У строгости есть цена: честно заявленный грейд тест подтверждает в 72 случаях из 100, остальным предлагает пересдать или ставит ступень ниже. Всё это посчитано на смоделированных кандидатах (`python -m app.validation.assessment --n 2000 --seed 7 --parity`).

## Проверьте нас за 3 минуты

- **Входы.** `jury1@demo.talent` … `jury10@demo.talent` (кандидат с нуля), `hr@sibcode.demo` (работодатель), `fsp001@demo.talent` (кандидат с ФСП); пароль `demo12345`.
- **Три клика до результата теста.** [/jury](https://89-124-65-102.sslip.io/jury) → «Режим эксперта», выбрать уровень → «Запустить тест»: адаптивный тест на виртуальном кандидате по шагам, оценка уровня ± погрешность и итоговый грейд. Без входа, в базу ничего не пишется.
- **Одна команда, которая пересчитывает главные цифры.** `make validate` (после `make demo`): психометрия теста и атака «20 сессий», подбор против базовых методов с доверительными интервалами, ось ФСП. Каждый шаг завершается проверкой порогов (`checks: passed`). Около 4 минут на обычном ноутбуке.

Без всяких ключей `make demo` поднимает всю платформу: тест, подбор, удостоверения, модерация, почта в Mailpit; резюме разбирается правилами.
Если добавить ключи, GigaChat или YandexGPT (`.env`) добавляют подсказки навыков с дословной цитатой из резюме; балл и грейд по-прежнему считает платформа.
**Расширения.** Вход через ФСП ID (OIDC, Keycloak) и HTTP-клиент реестра ФСП готовы к подключению боевых адресов.

Тест, подбор, приглашения, согласия, удостоверения и модерация работают на стенде по-настоящему. Имитируем мы только вот что:

- ФСП ID и реестр ФСП: демо-провайдер и демо-реестр с тем же протоколом, что у настоящих; подключение — настройки в `.env`.
- Связь с ATS: готовы вебхуки и выгрузка, коннектора к конкретной ATS пока нет.
- Данные синтетические: кандидаты, компании и проверка качества построены на сгенерированных данных, разметки людьми нет.
- Реестр ФСП пока только дописывается: новые протоколы приходят, но если Федерация исправит или аннулирует протокол задним числом, у нас старая строка не удалится сама. Аннулированные строки не попадают в публичную выдачу, а полную сверку строк по событию мы сделаем при интеграции с настоящим реестром.
- Вход через ФСП ID защищён PKCE и одноразовым state, но параметр nonce из OpenID Connect мы не передаём и не проверяем. Для демо-провайдера это неважно, к настоящему Keycloak Федерации его нужно добавить.
- Банк заданий узок для части специализаций: внутри mobile одно семейство видят 72 % сессий при нашей цели не выше 40 % (frontend 70 %, fullstack 68 %). Ответ от чужого экземпляра проходит в 0 % случаев, но банк для этих специализаций нужно расширять.
- Стенд для показа стоит вне РФ; в рабочей установке решение разворачивается на сервере Федерации.

- **Ключи заданий проверены запуском.** `python -m app.validation.key_check --variants 20`: 1875 исполненных вариантов, совпали с ключом все 1875; 25 вариантов на Java на машине без Java не проверены и посчитаны отдельно ([подробно](docs/VALIDATION_ASSESSMENT.md#как-устроен-тест)).
- **Повтор всей процедуры до итогового грейда.** κw двух путей **0,85** (зёрна 201–205, «не подтверждён» стоит ниже стажёра); при старом порядке шкалы — 0,76. Строгая цифра рядом: тот же грейд при повторе у 65,2 %, тот же или соседний — у 99,7 % ([таблица](#наши-цифры-на-общепринятой-шкале)).
- **Сопоставимые строки валидации.** Завышенный в анкете грейд не подтверждён в 92,6 % (зерно 7) / 92,3 % (201–205); решение «сдал / не сдал» верно в 77,8 % против 71,5 % у «верить анкете» на зерне 7 и 77,8 % против 73,6 % на отложенных зёрнах 201–205 ([сопоставимые строки](docs/VALIDATION_ASSESSMENT.md#сопоставимые-строки)).

- **Кривые сигналов честности.** На пороге продукта баллы риска ловят 90,0 % сессий с утечкой ключей при 0,7 % ложных срабатываний на честных; сигналы только просят посмотреть человека и грейд не меняют ([кривые](docs/VALIDATION_ASSESSMENT.md#кривые-сигналов-честности)).
- **EAP против WLE.** Оценщик продукта (EAP) не хуже альтернативы: κw 0,925 против 0,929, RMSE 0,269 против 0,271; менять нечего ([сравнение](docs/VALIDATION_ASSESSMENT.md#оценка-способности-eap-против-wle)).

Термины из таблицы простыми словами:

| Термин | Что значит |
|---|---|
| IRT 3PL | Статистическая модель теста: связывает уровень человека, сложность задания и шанс угадать ответ |
| Адаптивный тест | Следующее задание выбирается по предыдущим ответам, поэтому заданий нужно меньше |
| AUC | Как часто тест ставит более сильного кандидата выше более слабого: 1 — всегда, 0,5 — наугад |
| nDCG@10, P@10 | Качество первой десятки подборки: насколько верен порядок и какая доля в ней подходит |
| Спирмен | Насколько порядок кандидатов совпадает с их настоящей силой: 1 — полностью, 0 — никак |
| LCB | Осторожная нижняя оценка уровня по истории ФСП: один удачный старт не выглядит как стабильный уровень |
| p95 | Время, быстрее которого приходят 95 % ответов |
| RLS | Правило в самой базе данных: запрос не видит чужие строки, даже если в коде ошибка |
| TOTP | Одноразовый код из приложения-аутентификатора, второй шаг входа |
| OpenID Connect, PKCE | Стандартный вход через внешний сервис (ФСП ID) с защитой кода входа от перехвата |
| W3C Verifiable Credentials | Удостоверение с цифровой подписью: подлинность проверяет любой без запроса в ФСП |

## Наши цифры на общепринятой шкале

Сначала коротко и без формул. Всё ниже посчитано на смоделированных кандидатах, у которых настоящий уровень известен заранее; на живых людях цифры ещё предстоит подтвердить в пилоте.

- Приукрасивших мы ловим: из 100 человек, завысивших грейд в анкете, тест не подтверждает около 93. Честно заявленный грейд подтверждается у 72 из 100, остальным мы предлагаем пересдать.
- Решение «тянет / не тянет заявленный грейд» верно в 78 случаях из 100, а если просто верить анкете, то в 72.
- Если человек пройдёт всю процедуру дважды, грейд совпадёт в 65 случаях из 100, а с точностью до соседней ступени — почти всегда.
- В первой десятке подборки подходящих людей больше, чем при сортировке по резюме (лучше в 57 вакансиях из 100), обычном поиске по словам (70 из 100) и сортировке по самоописанию (74 из 100).

| κw: грейд только по оценке способности θ̂ против истинного | 0,864 (95 % ДИ 0,852–0,876) / 0,871 | **κw грейда, который назначает продукт, против истинного: 0,51 / 0,53**. Продукт только подтверждает заявленный грейд и выше него не ставит | та же |
| Повтор: κw двух путей до итогового грейда («не подтверждён» стоит ниже стажёра) | **0,85** / 0,85 (все шесть зёрен 0,85–0,86); при исходном порядке, где «не подтверждён» стоит после lead, — 0,76 / 0,75 ± 0,04 | тот же грейд при повторе: 64,8 % / 65,2 %; κw повтора одного теста: 0,56 / 0,55 | `python -m app.validation.assessment --n 2000 --seed S` |
| Повтор: тот же итог у уверенных решений | 82,7 % / **80,3 %** | общий тот же итог: 75 % (зерно 7) | та же |
| Повтор: корреляция оценок θ̂ | 0,86 (зерно 7) | — | та же |
| AUC соседних грейдов, среднее | 0,919 (зерно 7) | — | та же |
| Подбор: nDCG@10 / P@10 | 0,652 / 0,636 (зёрна 2026–2028); 0,652 / 0,628 (отложенные 4001–4005) | против сортировки по резюме модель лучше в 57 % / 55 % потребностей, хуже в 42 % / 45 % | `python -m app.validation.matching --ladder` (и `--seeds 4001,4002,4003,4004,4005`) |
| Подбор: доля потребностей, где модель лучше базы | случайный 100 %, самоописание 74 %, BM25 70 %, резюме 57 % | отложенные зёрна: 100 / 63 / 65 / 55 % | та же |

Про κw двух путей: каппа штрафует промах по квадрату расстояния между грейдами, поэтому важно, где на шкале стоит «не подтверждён». Если ниже стажёра, как на шкале способности, получается 0,85; если в конце шкалы после lead, получается 0,76. Строгая цифра рядом: тот же грейд при повторе получают около 65 % людей.

## Как работают тест, подбор и ось ФСП

### Тест на грейд

ТЗ отвергает единый набор заданий (ответы разойдутся) и генерацию нейросетью (сложность несравнима). Мы выбрали **параметрические семейства**: шаблон задания, параметры и код, который вычисляет правильный ответ.

- Каждый кандидат получает новые числа, строки и фрагменты кода, а сложность задаёт уровень семейства. Выученный ответ не подходит: ключ чужого экземпляра того же семейства сдаёт 0 %.
- 22 семейства заданий (`backend/app/items/registry.py`): 20 с вычисляемым ответом (включая Docker, Kubernetes и Linux shell) и 2 концептуальных пула. Отдельный тест перезапускает фрагменты и сверяет ключ. Отчёт `python -m app.validation.key_check --variants 20`: 1875 исполненных вариантов (Python, Node.js, SQLite, bash, Go), 1875 совпали с ключом; 25 вариантов на Java не исполнялись, потому что на машине прогона нет Java (подробно — [VALIDATION_ASSESSMENT](docs/VALIDATION_ASSESSMENT.md)).
- Целочисленный ответ вводится с клавиатуры: угадать нельзя, и на границе грейда такое задание даёт в 1,7 раза больше информации, чем выбор из четырёх.
- Задания выбираются адаптивно по модели IRT 3PL: следующее задание точнее всего различает уровни у порога заявленного грейда. Тест заканчивается за 8–20 заданий, как только уровень определён с уверенностью 90 %.
- Грейд мы подтверждаем при вероятности от 75 %. Уверенный результат выше (от 90 % за следующий порог) только предлагает отдельный тест на ступень выше. Подтверждённый грейд не понижается. Если кандидат не сдал, тест на уровень ниже доступен сразу, пересдача того же уровня — через 7 дней, следующее повышение после смены грейда — через 90 дней.
- Сессию и банк мы защищаем так: правильный ответ не уходит в браузер до конца теста, ответ принимается по HMAC-токену только на текущее задание, время засекает сервер. Ключ, доля верных ответов по которому растёт сверх ожидаемой (z или накопленная сумма), уходит в карантин; статистика открыта: `GET /api/v1/public/assessment/items`.
- Регулярные задания пишет работодатель. Если у задания есть эталон, ответ проверяет система, а открытое задание проверяет сам работодатель. Вердикт виден в карточке и грейд не меняет. Раз в неделю платформа сама собирает короткую задачу из вакансии специализации кандидата.

Во время теста языковая модель не вызывается: сложность у всех измеряется одной шкалой. Подробно: [SOLUTION.md, гл. 3](docs/SOLUTION.md#3-механика-тестирования).

### Подбор

Работодатель описывает **потребность**: специализация, грейд, обязательные и желательные навыки, предметная область, чем занимается команда. Каждое изменение сохраняется новой версией, отобранные кандидаты помнят, по какой версии их выбрали.

Порядок выдачи задаёт одна оценка, которую можно разложить на части (`backend/app/services/matching.py`):

```math
\mathrm{fit} = \frac{\sum_{f \in \text{названы}} w_f\, s_f}{\sum_{f \in \text{названы}} w_f},\qquad
w = \{\text{навыки } 0{,}50;\ \text{грейд } 0{,}20;\ \text{специализация } 0{,}20;\ \text{текст } 0{,}05;\ \text{область } 0{,}05;\ \text{город и формат } 0{,}05\}
```

```math
E = T + 0{,}5\cdot\max(0,\ F - T),\qquad \text{нет истории ФСП}\Rightarrow E = T,\quad \text{нет теста}\Rightarrow E = F
```

```math
\mathrm{employer} = \frac{\mathrm{fit} + 0{,}40\cdot E\cdot \text{близость}}{1 + 0{,}40},\qquad
\text{итог} = \frac{2\cdot \mathrm{employer}\cdot p_{\text{accept}}}{\mathrm{employer} + p_{\text{accept}}} - \min\bigl(0{,}10,\ 0{,}02\cdot\max(0,\ n_{\text{приглашений}} - 2)\bigr)
```

Фактор, которого потребность не называет, выпадает, остальные веса перенормируются. $T$ — фактор теста, $F$ — фактор оси ФСП (`FSP_LIFT = "boost"`). Гармоническое среднее с вероятностью $p_{\text{accept}}$, что кандидат примет вилку, — только если вилку назвали обе стороны; иначе $\text{итог} = \mathrm{employer}$ минус тот же штраф. Код: `backend/app/services/matching.py` (`EVIDENCE_WEIGHT`, `CONGESTION_STEP`, `CONGESTION_CAP`, `_harmonic`).

- Навык весит по силе доказательства: подтверждён тестом 1,0, найден цитатой в резюме 0,75, заявлен 0,55. Заявленный грейд весит 0,85 от подтверждённого.
- «Близость» — насколько кандидат совпадает с запрошенной специализацией и грейдом. Поэтому сильный профиль из другой категории не обгоняет подходящий, а внутри категории выше тот, у кого сильнее тест и протокол ФСП.
- Ось ФСП может только поднять оценку над тестом: привязка ФСП ID никогда не опускает кандидата (тест свойств на случайных историях `tests/unit/test_fsp_lift_property.py`). Нет истории ФСП — ось не учитывается и не штрафует.
- Имя, пол, возраст и регион в оценку не входят.

Под каждой карточкой — строки «плюс / минус / инфо» по факторам с кодом причины, «лучше N % кандидатов категории», результат последней практики и вердикт по заданию работодателя. Подробно: [SOLUTION.md, гл. 4](docs/SOLUTION.md#4-механика-подбора-и-категоризация).

### Ось «подтверждено ФСП»

Грейд и результаты соревнований — разные вещи, и платформа их не смешивает. Грейд подтверждает только основной тест специализации. Результаты ФСП влияют на место внутри категории, но не на грейд. Ось «подтверждено ФСП» считается отдельно, версия методики `v4.1.0` (с 11.10.2026: участие не входит в балл, нижняя граница — лучшее подмножество, поэтому ось монотонна: новый результат никогда не понижает оценку):

$q$ — класс результата по месту и размеру поля $N$: победитель 1,00 · призёр (2–3 место) 0,85 · топ-10 % 0,65 · верхняя половина 0,45 · участие 0 (победитель и призёр — при $N \ge 6$; статус соревнования не учитывается). Не больше 2 результатов в месяц на дисциплину (сильнейшие); в сумму входят только события с $q > 0$, участие учитывается в профиле, но не в балле.

```math
w = \frac{2^{-\text{месяцы}/18}}{\sqrt{\text{размер команды}}}\cdot\left(1 - e^{-N/30}\right)
```

```math
\mu = \frac{\sum w\,q + K\mu_0}{\sum w + K},\qquad \sigma = \sqrt{\frac{0{,}04}{\sum w + K}},\qquad K = 2,\ \mu_0 = 0{,}30
```

```math
\mathrm{LCB} = \max_{S,\ |S| \le 5}\ (\mu_S - \sigma_S)
```

Пустое подмножество — нижняя граница; ранжирование по LCB. Код: `backend/app/services/scoring/engine.py` (`HALF_LIFE_MONTHS`, `FIELD_SCALE`, `PRIOR_STRENGTH`, `PRIOR_MEAN`, `PRIOR_VAR`).

Федерация посоветовала не ранжировать соревнования по статусу: все соревнования одинаково важны. Поэтому качество результата зависит только от места: победа, призовое место или участие. В подборке по потребности профильная дисциплина входит целиком, а результат другой дисциплины — с весом 0,5. Для безопасности протокол по ИБ важнее протокола по робототехнике. Специализация без профильной дисциплины берёт лучший результат по всем дисциплинам. Это байесовская оценка с нормальным априорным распределением N(0,30; τ²/K) и известной дисперсией наблюдения τ² = 0,04; веса w работают как дробные наблюдения. Ранжирование по нижней границе LCB = μ − σ. Это консервативная оценка, а не доверительный уровень: выбор лучшего подмножества смещает её вверх, поэтому процент уверенности мы не указываем. Поэтому один случайный успех не обгоняет стабильную серию. Участие весит 0 и в балл не входит: оно не поднимает и не опускает оценку, накрутка участий равна пустой истории. Из результатов берётся подмножество до пяти событий с наибольшей нижней границей, поэтому добавленный результат не может понизить LCB (тест свойств `tests/unit/test_fsp_engine_monotone.py`). Вес результата растёт с размером поля N как 1 − e^(−N/30): место среди 6 весит около пятой доли места среди 200. В пул идут не больше двух результатов за календарный месяц. Любое число призовых мест в полях по 6 человек остаётся ниже одной победы среди 200 (`tests/unit/test_fsp_small_field.py`). Командный результат снижает вес доказательства и расширяет σ, но не снижает уровень; вклад внутри команды не разделяется. Разряд (МС, КМС, I–III, I–III юношеские) приходит из реестра ФСП вместе с датой и номером приказа. Платформа его не вычисляет из места. В оценку он не входит, фильтр «Разряд не ниже» смотрит на этот факт реестра.


Вход через ФСП ID — OpenID Connect с PKCE, как в Keycloak Федерации; подключение настоящего провайдера — пять настроек в `.env`. Из реестра берутся строки протокола и присвоенные разряды; пол, контакты и документы не запрашиваются. Каждая строка протокола выдаётся как W3C Verifiable Credential 2.0 (`eddsa-jcs-2022`), подпись проверяет любой: `POST /api/v1/public/credentials/verify`. Схема обмена и контракт реестра: [docs/FSP_INTEGRATION.md](docs/FSP_INTEGRATION.md).

| Подборка на 10 000 профилях, 2 процесса API, p95 | 360 мс | `python tests/load_api.py --scenario shortlist --seconds 60 --reuse`, банк 10 000 |
| Юнит-тесты (в CI, со всеми компиляторами) | 1117 | `python -m pytest tests/unit --collect-only -q` |
| Покрытие приложения, сервисы и API | 73,1 %, 75 % и 61 % (Python 3.12, допуск ±0,5 п. п.) | `python -m pytest tests/unit -q --cov=app --cov-report=json --cov-fail-under=65` и `python tests/coverage_lines.py` |
| Покрытие вместе с интеграционными тестами | порог: приложение от 72 %, pipeline и assessment от 60 % | `python tests/integration_coverage.py` |
| Тесты интерфейса | 110 | `npm test` в `frontend/` |
| Проверки Playwright | 67 | `npx playwright test --list` в `frontend/`: 7 сквозных сценариев и 60 проверок доступности |

**Почему строка «без теста и без ФСП» выше полной модели по nDCG@10 (0,669 против 0,652).** nDCG@10 смотрит только на то, совпала ли категория и подходит ли человек по навыкам. Что внутри категории он сильнее, метрика почти не замечает. Без теста и ФСП модель ставит наверх тех, у кого больше заявлено. По метрике это выглядит лучше, а работодатель на деле получает:

| Те же три зерна, `python -m app.validation.matching` | Полная модель | Без теста и без ФСП |
|---|---|---|
| Порядок внутри категории, Спирмен со скрытой силой | 0,374 | 0,016 |
| Завышенный грейд в первой десятке | 21,5 % | 27,6 % |
| Настоящий грейд ниже грейда потребности, первая десятка | 14,7 % | 24,7 % |

Тест и ФСП почти не меняют, какие люди в принципе подходят. Они решают, кто из подходящих окажется первым, и убирают из первой десятки тех, кто завысил себе грейд. Поэтому продукт ранжирует полной моделью, а nDCG@10 стоит в таблице рядом со Спирменом и долей завышенных, без отбора. Отдельно про ФСП: подъём по результатам соревнований **не улучшает** nDCG@10. На отложенных зёрнах 4001–4005 он его слегка снижает (Δ −0,015, 95 % ДИ −0,020…−0,010, собственный порог −0,005, [таблица](docs/VALIDATION_MATCHING.md#11102026-подъём-на-отложенных-зёрнах-результат-приёмки-и-следующий-шаг)), а Спирмен внутри категории почти не меняет (+0,007). В продукте ось ФСП служит проверяемым сигналом и задаёт порядок среди равных по категории. Мы включили её по ТЗ 2.1 как дополнительное доказательство, качество подборки она не поднимает.

**Категоризация (ТЗ 6.2: по стеку, специализации и пройденным тестам).**
- Специализация: тест собирается только из семейств своей специализации, смешения нет по построению ([план теста](docs/VALIDATION_ASSESSMENT.md)).
- Грейд по пройденному тесту, одна сессия: точно 57,4 %, ±1 ступень 84,7 % (шесть ступеней от «ниже стажёра» до lead); после пути — 64,5 % и 98,9 %. `python -m app.validation.assessment --n 2000 --seed 7`.
- Стек: навык становится `test_confirmed` при ≥ 75 % верных на ≥ 3 заданиях по нему и в профиле отличается от заявленного; точность разбора резюме по полям — отдельная валидация NLP.

**Пилот с ФСП (предлагаемый дизайн; эталона в хакатоне нет).** Мы предлагаем взять 150 участников ФСП на 6 недель. Каждый проходит тест и техническое интервью у двух экспертов, которые не видят результата теста. Критерии успеха: взвешенная каппа грейда теста с консенсусом экспертов ≥ 0,60 при каппе между экспертами ≥ 0,70; иначе пороги не публикуются как подтверждённые. После ≥ 30 ответов на ключ сдвиги трудности заданий пересчитываются `python -m app.validation.calibrate`, после чего валидация повторяется на отложенной половине участников.

Методика и полные таблицы: [проверка теста](docs/VALIDATION_ASSESSMENT.md), [проверка подбора](docs/VALIDATION_MATCHING.md), [ось ФСП](docs/FSP_INTEGRATION.md#4-как-результат-становится-доказательством), [нагрузка](docs/LOAD_TEST.md). Жюри может проверить подбор на своей разметке: `python -m app.validation.matching --import pairs.json`.

Сквозные сценарии Playwright (`frontend/e2e/journeys.spec.ts`) сами читают код подтверждения из Mailpit на http://localhost:8025: регистрация, письмо, вход. Почта наружу не уходит. Запуск: `npx playwright test e2e/journeys.spec.ts` в `frontend/` при поднятом `make demo`.

Сигналы честности на модели (`python -m app.validation.detector_curves`, отложенные зёрна 201–205): на порогах продукта баллы риска ловят 90,0 % сессий с утечкой половины ключей при 0,7 % ложных у честных; согласованность ответов lz* — только 37,4 % при 5,1 %, поэтому она лишь помечает сессию. Таблица по порогам — в [VALIDATION_ASSESSMENT](docs/VALIDATION_ASSESSMENT.md#кривые-сигналов-честности).

## Границы применимости

Что измерено и как улучшим — каждое ограничение один раз:

- **Данные синтетические.** Все метрики посчитаны на смоделированных кандидатах с фиксированными зёрнами и отложенными зёрнами. Дальше нужен пилот на данных ФСП.
- **Разметка 200 пар для протоколов подбора** сделана двумя автоматическими оценщиками на основе языковых моделей, не людьми ([подробности](docs/VALIDATION_MATCHING.md)). Следующим шагом её повторят HR-эксперты.
- **Экспозиция заданий:** самый частый ключ внутри специализации видят 50–65 % сессий при цели 40 % ([раздел](docs/VALIDATION_ASSESSMENT.md)). Мы пополним банк ключами нужного уровня.
- **Подбор против поиска по ключевым словам:** nDCG@10 0,607 против 0,399 у BM25 на той же разметке. Абсолютное значение зависит от жёсткости синтетики (завышенный грейд, шум в навыках).
- **Демо-стенд размещён в Нидерландах** и работает только на тестовых данных. Промышленный контур с персональными данными разворачивается в РФ (152-ФЗ, ст. 18 ч. 5).

## Внедрение в ФСП

- **Реестр ФСП → API → профиль.** Сервис забирает протоколы соревнований по контракту реестра ([FSP_INTEGRATION.md §2–3](docs/FSP_INTEGRATION.md)); результат становится отдельной осью «подтверждено ФСП» в профиле и подборе (§4–5).
- **Вход через ФСП ID.** OpenID Connect с PKCE S256; совместим с Keycloak Федерации, пространство Keycloak (realm) `fsp` входит в Compose, что настроить — [FSP_INTEGRATION.md §1](docs/FSP_INTEGRATION.md#1-вход-через-фсп-id-openid-connect-keycloak).
- **Лицензии и стек.** Только открытые компоненты, перечень с версиями и лицензиями — [docs/THIRD_PARTY.md](docs/THIRD_PARTY.md). Работает на своих серверах в Docker, внешние облачные сервисы не нужны; языковая модель необязательна. Совместимость с конкретными продуктами из реестра отечественного ПО не проверялась.
- **152-ФЗ.** Отдельные согласия, локализация баз в РФ при эксплуатации, шифрование контактов, журнал доступа — [раздел ниже](#персональные-данные-и-безопасность) и [SOLUTION.md §10](docs/SOLUTION.md).

## Персональные данные и безопасность

- Против массовых рассылок: компания с подтверждённой почтой отправляет до 10 приглашений в сутки, после проверки ИНН, почты на домене сайта или статуса партнёра ФСП — до 50 (`INVITE_LIMIT` в `backend/app/services/trust_level.py`). Одному кандидату компания держит одно активное приглашение; после отказа повторно пригласить можно через 30 дней (`DECLINE_PAUSE` в `backend/app/services/offers.py`). Если хранилище лимитов недоступно, приглашение не уходит.
- Отдельные согласия на обработку (ст. 9 152-ФЗ) и на распространение для публичной страницы (ст. 10.1), в базе — версия и SHA-256 принятого текста.
- Карточка в выдаче анонимна. Контакты — только после принятия приглашения или собственного отклика и при действующем согласии. Каждый просмотр записывается в журнал доступа.
- Отзыв согласия закрывает контакты сразу, через 30 дней данные стираются (ст. 21). Удаление аккаунта стирает их немедленно, вместе с ответами на задания и сообщениями. Контакты можно закрыть и для одной компании: она получает 403 `contacts_revoked`.
- Кандидат 15–17 лет попадает в поиск только после согласия законного представителя по подписанной ссылке (ч. 6 ст. 9).
- Зарплатная вилка указывается до вычета НДФЛ, это написано у полей.
- Пароли — Argon2id (параметры OWASP; старый хеш bcrypt при входе проверяется и сразу переписывается), коды подтверждения хранятся только как HMAC, ключ подписи токенов уникален для установки. Лимиты на вход, регистрацию, письма, приглашения и поиск; при недоступном хранилище лимитов вход закрывается.
- Контакты в базе зашифрованы AES-256-GCM. Строки закрыты политиками PostgreSQL (RLS): на сервере API, worker и beat входят ролью `fsp_app` без прав суперпользователя и без `BYPASSRLS`. Обход всех маршрутов с чужим идентификатором в `tests/smoke_api.py`: 0 ответов 2xx из 240 запросов.
- Решение о найме принимает человек: платформа ранжирует и объясняет, но не отсеивает (ст. 16).
- Языковая модель (GigaChat или YandexGPT, только российские облака) получает обезличенный текст и предлагает навыки с дословной цитатой из резюме. Балл, порядок выдачи и грейд она не меняет. Без ключа или при сбое модели резюме разбирается правилами.
- Пульт модерации закрывается вторым фактором (TOTP, RFC 6238). Код кандидата выполняется в контейнере `sandbox` без сети, с корнем только для чтения и лимитами памяти, процессора и времени.

Полный разбор и сверка с OWASP ASVS: [SOLUTION.md, гл. 10](docs/SOLUTION.md#10-безопасность-и-152-фз).

## Запуск у себя за 5 минут

Одна команда на свежем клоне. Ничего править не нужно: файл `.env` не обязателен, демо-данные загружаются сами.

```bash
git clone https://github.com/KonkovDV/fsp-talent.git
cd fsp-talent
docker compose up -d --build --wait
```

Команда возвращает управление, когда всё готово: база, API, фоновые задачи и демо-данные. Дальше:

| Адрес | Что там |
|---|---|
| http://localhost | Кабинеты кандидата и работодателя, страница жюри `/jury` |
| http://localhost/docs | Swagger UI, спецификация OpenAPI 3.1 |
| http://localhost:8025 | Mailpit: письма с кодами подтверждения |
| http://localhost/health | Состояние стенда |

Демо-входы те же, что на стенде, пароль `demo12345`: `jury1@demo.talent` … `jury10@demo.talent`, `hr@sibcode.demo`, `fsp001@demo.talent`.

Проверить, что демо-данные на месте (должно быть «18/18 OK»):

```bash
docker compose run --rm backend python -m seed.demo_check
```

Остановить и удалить всё, включая данные: `docker compose down -v`.

**Что нужно.** Docker 24+ с Compose 2.24+ (Docker Desktop 4.27+), 4 ГБ свободной памяти, 5 ГБ на диске, свободный порт 80. Видеокарта, Python, Node.js и `make` не нужны. С `make` то же самое: `make demo`, проверка до запуска: `make doctor`.

**Сколько ждать.** Первый запуск занимает 5–10 минут, пока скачиваются и собираются образы. Повторный проходит за секунды.

**Если что-то не так**

| Ситуация | Что сделать |
|---|---|
| Порт 80 занят (`port is already allocated`) | `HTTP_PORT=8080 PUBLIC_BASE_URL=http://localhost:8080 docker compose up -d --build --wait`, сайт будет на http://localhost:8080. Порты почты и API так же: `MAIL_PORT`, `API_PORT`, `FRONTEND_PORT`. Значения можно записать в `.env` |
| Mac на Apple Silicon (M1–M4) | Команды те же. Базовые образы публикуются под arm64, сборка идёт нативно |
| Windows | Docker Desktop с WSL 2. Команды те же, в PowerShell. Клонируйте лучше внутрь WSL (`\\wsl$\...`), так сборка быстрее. Без `make` есть `powershell -ExecutionPolicy Bypass -File scripts\start-local.ps1` |
| `unknown flag: --wait` или ошибка про `env_file` | Старый Compose. Обновите Docker Desktop, или создайте `.env` (`cp .env.example .env`) и запустите `make demo` |
| Сборка упала на `apt-get`, `pip` или `npm` | Нет доступа к зеркалам или к прокси. Повторите команду: кэш сохранится, сборка продолжится с места остановки |
| Что-то не стало `healthy` | `docker compose ps` и `docker compose logs backend demo-seed` |

**Без интернета.** Нужен только для первой сборки (образы, pip, npm). После неё стенд работает полностью офлайн: внешних вызовов нет, языковые модели по умолчанию выключены, почта уходит в локальный Mailpit. Чтобы запустить на машине без сети, соберите на машине с сетью и перенесите образы: `docker save` и `docker load`.

Подробности и частые проблемы — [docs/INSTALL.md](docs/INSTALL.md).

## Демо-режим и промышленный контур

- **Качество измерено на синтетике со скрытой правдой.** Так точность грейда и порядок выдачи считаются честно, по известному ответу. Для живых данных готова калибровка трудностей и весов: `python -m app.validation.calibrate`. Подбор на своей разметке жюри проверяет на [/evaluate](https://89-124-65-102.sslip.io/evaluate) или командой `python -m app.validation.matching --import pairs.json`.
- **ФСП ID и реестр ФСП** на стенде работают через имитацию с тем же протоколом: OIDC с PKCE и контракт реестра из [FSP_INTEGRATION.md](docs/FSP_INTEGRATION.md). Переход на Keycloak Федерации — пять настроек в `.env`, на HTTP-клиент реестра — `FSP_MODE=real`.
- **Смысловой поиск и локальная модель сравнения пары «потребность — кандидат»** включаются аргументом сборки `INSTALL_RERANKER=1`; публичный стенд работает на процессоре без них.
- **Накрутка навыков ограничена.** Если 20 % кандидатов допишут себе все навыки специализации, их доля в топ-10 вырастет с 17,8 % до 30,5 %. У поиска по словам она вырастает до 44,9 %, а если не отличать заявленное от подтверждённого — до 66,8 %. Мы планируем снизить вес навыков, не подтверждённых тестом ([VALIDATION_MATCHING.md](docs/VALIDATION_MATCHING.md#атака-накруткой-навыков)).
- **Локализация ПДн (ч. 5 ст. 18 152-ФЗ)** обеспечивается местом установки: решение разворачивается целиком на сервере Федерации. Демонстрационный стенд её не обещает.
- **ЕГРЮЛ, ЕСИА и выдача удостоверений в кошелёк по OID4VCI** подключаются на контурах Федерации и государства без смены формата удостоверений (`eddsa-jcs-2022`).

Демо-режим (`DEMO_MODE=true`) включён только на стенде для жюри:

| На демо-стенде | В установке для настоящих пользователей (`DEMO_MODE=false`) |
|---|---|
| Аккаунты `jury1@demo.talent`…`jury10@demo.talent` проходят полный тест без пауз и лимитов попыток; кнопка «Взять свободный аккаунт жюри» (`GET /api/v1/public/jury-free`) | Обычные правила: пересдача уровня через 7 дней, повышение после смены грейда через 90 дней; этот адрес API выключен |
| Пробный тест: до 15 заданий за 5 минут, грейд не подтверждает | Нет |
| «Войти гостем без почты» на 48 часов | Нет |
| Вход через ФСП ID — помеченная страница провайдера на этом сайте (`FSP_ID_MODE=mock`) | Keycloak Федерации (`FSP_ID_MODE=oidc`); имитация без `DEMO_MODE` не запускается |

## Вопросы жюри

**Чем тест защищён от утечки ответов?** Задания генерируются из параметрических семейств, правильный ответ не уходит в браузер до конца теста, ответ принимается по HMAC-токену только на текущее задание, а ключ с аномальным ростом доли верных ответов уходит в карантин. Цифры устойчивости к утечке — в [проверке теста](docs/VALIDATION_ASSESSMENT.md).

**Почему нейросеть не генерирует задания?** ТЗ требует сопоставимой сложности. Во время теста языковая модель не вызывается: сложность задаёт уровень семейства, и все кандидаты измеряются одной шкалой IRT.

**Что, если у кандидата нет истории ФСП?** Ось ФСП не учитывается и не штрафует: оценка строится по тесту и опросу (`combine_evidence` в `app/services/matching.py`, аккаунт `nofsp@demo.talent`).

**Может ли работодатель увидеть контакты без согласия?** Нет. Контакты отдаются только после принятия приглашения или собственного отклика кандидата, каждый просмотр пишется в `access_logs`, кандидат может закрыть контакты для одной компании (`contacts_revoked`).

**Как подключить настоящий ФСП ID и реестр?** Пять настроек `.env` для Keycloak Федерации и `FSP_MODE=real` для реестра — [FSP_INTEGRATION.md](docs/FSP_INTEGRATION.md).

**Где API?** Swagger UI на [/docs](https://89-124-65-102.sslip.io/docs), спецификация [/openapi.json](https://89-124-65-102.sslip.io/openapi.json), снимок `docs/openapi.json` сверяется с приложением тестом `test_openapi_paths.py`, коды ошибок — [API_ERRORS.md](docs/API_ERRORS.md).

**Как убедиться, что цифры не нарисованы?** Каждая строка таблицы [цифр](#цифры-которые-можно-проверить) содержит команду с фиксированным зерном; `python tests/doc_numbers.py` сверяет опубликованные значения со свежим прогоном.

**Повтор и разделяющая сила посчитаны на синтетике — что это доказывает?** Что процедура различает уровни, когда правда известна: 2000 кандидатов с заданной θ, AUC соседних грейдов в среднем по парам 0,919, у уверенных решений повтор на новых заданиях даёт тот же итог в 82,7 % случаев (80,3 % в среднем на отложенных зёрнах 201–205) ([проверка теста](docs/VALIDATION_ASSESSMENT.md)). Те же проверки повторены с моделью, которую оценщик не знает (раздел «Ошибка модели, фиксированная форма, чужие сессии»). Живого повтора нет: людей с проверенным грейдом у хакатона нет, его даст пилот с ФСП с двумя слепыми экспертами ([план пилота](#цифры-которые-можно-проверить)).

**Почему уверенный результат не поднимает грейд сразу?** Так ответили постановщики на Q&A: на вопрос «сразу присвоить middle после уверенного junior или отдельный тест на middle?» — «Желательно отдельный тест». Тест на грейд G подтверждает G или ничего; если вероятность выше следующего порога от 90 %, кандидат получает предложение пройти отдельный тест на ступень выше (`backend/app/services/assessment.py:10-12`). Ограничение частоты считает только фактическую смену грейда.

**Одно задание видят 72 % сессий mobile — банк слишком мал?** Доля считается по ключу «семейство и уровень», а не по тексту: каждый показ — новый экземпляр с другими числами и кодом, и ответ от чужого экземпляра проходит в 0 % случаев. По всем специализациям максимальная доля ключа — 41 %; 72 % внутри mobile, 70 % у frontend и 68 % у fullstack дают одно семейство JavaScript при 25–50 % JavaScript в их плане ([таблица экспозиции](docs/VALIDATION_ASSESSMENT.md#симуляция)). Банк расширяется новыми семействами для frontend, mobile и devops.

**Почему нет прокторинга с камерой?** Мы отказались от него сознательно. Изображение лица для проверки личности — биометрические персональные данные (ст. 11 152-ФЗ, только с письменного согласия), а тест подтверждает грейд, решение о найме принимает работодатель после собеседования. Вместо камеры у нас новый экземпляр задания на каждый показ, время на сервере, отметки об уходе со вкладки и копировании условия (`backend/app/services/session_marks.py`). Такая попытка стоит в подборке ниже (место × 0,85) с видимой работодателю строкой, грейд не меняется. Механика теста и его защиты — [SOLUTION.md, гл. 3](docs/SOLUTION.md#3-механика-тестирования).

**Кто модерирует вакансии?** Стол «Модерация» (`/employer/moderation`) для сотрудников, которым права выданы с консоли сервера: жалобы кандидатов с выгрузкой в CSV, закрытие вакансии, закрытие входа компании, флаги заниженных вилок (`backend/app/api/v1/moderation.py`). Опубликованный демо-аккаунт работодателя его не открывает. До человека работают правила: вилка не ниже МРОТ обязательна, без ИНН — 10 приглашений в сутки и одна вакансия, порог жалоб замораживает рассылку ([TRUST_AND_ATS.md](docs/TRUST_AND_ATS.md)).

**Совпадает ли результат с экспертной оценкой?** Для подбора лист на 200 пар для двух людей готов, слепой: только наблюдаемый профиль, без балла модели; каппа двух разметчиков и пересчёт метрик по их оценкам — одной командой ([разметка людьми](docs/VALIDATION_MATCHING.md#слепая-разметка-лист-и-расчёт)). Сейчас каппа 0,46 посчитана против синтетического разметчика, людьми лист ещё не размечен. Для теста эталон даст пилот: взвешенная каппа грейда с консенсусом двух экспертов не ниже 0,60, иначе пороги не публикуются как подтверждённые. Жюри может проверить подбор на своих парах: `python -m app.validation.matching --pairs ../docs/examples/jury_pairs.jsonl`.

**Зачем это производственной компании, а не ИТ-компании?** Разработчики, инженеры встраиваемых систем и специалисты по безопасности нужны и заводам, и за тех же людей компания конкурирует с банками и ИТ-фирмами. Платформа показывает кандидата, чей уровень проверен тестом, а не написан в резюме, и объясняет, почему он в подборке. Компания сама приходит к нему с вакансией и вилкой, а контакты открываются только с его согласия. Если нужна одна цифра: в первой десятке подборки завысивших себе грейд 21,5 % против 28,1 % при сортировке по резюме.

**Сколько времени экономит рекрутер?** Пока мы это не измеряли, это метрика пилота: время от описания потребности до принятого приглашения.

**Что готово для связи с ATS?** Подписанные вебхуки (стандарт Standard Webhooks) с журналом доставок, выгрузка данных, PDF-профиль кандидата и приём итога собеседования. В ATS уходят только кандидаты, которые сами согласились на контакт. Готового коннектора к конкретной ATS (Хантфлоу, Talantix, E-Staff) нет: сценарий для Хантфлоу описан в [TRUST_AND_ATS.md](docs/TRUST_AND_ATS.md), это первый шаг пилота.

**Как продукт связан с обучением?** После полного теста кандидат видит итог по темам. Есть задача недели из вакансий его специализации, задания работодателей и пробный тест. Рекомендаций курсов и плана обучения пока нет, это шаг после пилота.

**Стенд недоступен — что делать?** `make demo` поднимает то же решение локально за 5–10 минут с теми же демо-аккаунтами.
