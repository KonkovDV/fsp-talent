# Доступность и производительность UI

Прогон на локальном production-сборке (`vite build` + `vite preview`), 2026-10-11 (МСК).
Инструменты: `@axe-core/playwright` 4.13.0 (теги wcag2a/aa, wcag21aa, wcag22aa), Lighthouse 12 (mobile + desktop).
Скрипт: `frontend/scripts/measure-a11y-perf.mjs` (нужны `lighthouse` и `chrome-launcher` в node_modules).

## Страницы

Главная, вход, «Режим жюри», методика, кабинет кандидата (пример), тест (мок active), потребности (пример + подборка), поиск с карточками.

Темы: светлая и тёмная. Авторизованные экраны — режим «пример» (`fsp-auth.example`).

### Почему в первом прогоне desktop был 69–72

Ошибка замера, а не сайта. Скрипт передавал только `formFactor: 'desktop'`, и Lighthouse оставлял мобильное замедление (RTT 150 мс, CPU ×4), но оценивал по строгим порогам desktop (LCP «хорошо» ≤ 1,2 с против 2,5 с на mobile). LCP и FCP при этом совпадали с мобильными (≈ 2,5–2,7 с). С `desktopConfig` тот же экран даёт LCP 0,6 с и Perf 100. Элемент LCP везде — текстовый `<h1>`, не картинка: hero-изображений нет, крупных картинок без масштабирования тоже нет. Сдвига вёрстки на широких экранах нет (CLS ≈ 0).

Что тормозит mobile: блокирующие отрисовку `index.css` и `theme-init.js`. `theme-init.js` нужен, чтобы тёмная тема не мигала при загрузке, поэтому его не трогали. Шрифты подключены через `@fontsource-variable` с `font-display: swap`.

## Что сделано в этом прогоне

- Фикстура примера потребностей (`demoFallback`) с `params`, survey-options и подборкой — кабинет работодателя не падает без API.
- Защита рендера потребностей при отсутствии `params`.
- `PageHeader` выставляет `document.title` вида «… — ФСП Талант»; длинные заголовки с `overflow-wrap:anywhere`.
- `preview.proxy` для `/api` в `vite.config.ts` (удобство локального прогона).

Маршруты уже разбиты через `React.lazy` — дополнительных ленивых чанков не добавляли.
