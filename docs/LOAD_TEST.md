# Нагрузочная проверка

ТЗ 3.5: «стабильная работа при одновременном использовании десятками пользователей; основные операции — формирование подборки, открытие профиля, поиск — выполняются за приемлемое время».

## Как проверяли

Скрипт `backend/tests/load_api.py` регистрирует нужное число пользователей через API (коды подтверждения берёт из писем, как сквозная проверка), затем запускает их одновременно. Каждый пользователь повторяет обычные действия с паузой 0,5–1,5 секунды между запросами, как человек, который читает страницу:

- работодатели ищут по банку кандидатов (шесть разных запросов), открывают подборку по потребности, свои вакансии и профиль компании;
- кандидаты открывают профиль, вакансии под профиль, задачу недели и уведомления.

Команда на запущенном стенде:

```bash
make load
# или
docker compose exec -T -e SMOKE_BASE=http://localhost:8000/api/v1 -e MAILPIT_URL=http://mailpit:8025 \
  backend python tests/load_api.py --users 40 --seconds 60
```

## Результат

Стенд с демо-данными (153 кандидата, 9 вакансий), API в двух процессах uvicorn, PostgreSQL 16 и Redis 7 на той же машине: 2 ядра Intel Xeon 2,8 ГГц. Прогон 06.10.2026.

## Что ограничивает масштаб и как его поднять

- **Поиск** ограничен 30 запросами в минуту на работодателя: это защита от выгрузки базы, а не предел производительности. В прогоне лимит не сработал ни разу.
- **Подборка** считается на сервере приложения по кандидатам, прошедшим SQL-фильтры. В Redis на 300 секунд лежит один порядок и баллы: ключ `shortlist:{потребность}:{версия}:{эпоха банка}`. Эпоха увеличивается, когда меняется профиль, заканчивается тест, приходит синхронизация ФСП, меняются видимость, согласие или статус поиска, человек удаляет аккаунт или компания записывает итог собеседования. Одинаковые потребности без итога собеседования считают этот порядок один раз. Пометки компании — «в шорт-листе», «уже приглашён», «контакты закрыты» — в кэш не пишутся и подставляются после чтения, только для той компании, которая спросила. Правка потребности увеличивает версию, и старая запись больше не читается. Таблица ниже снята со старого кэша страниц на 60 секунд.
- **API без состояния**: процессы uvicorn масштабируются горизонтально (`--workers` или реплики контейнера `backend`), состояние сессий входа через ФСП ID и лимиты лежат в Redis.

## Большой банк

Команда `make load-big` добавляет синтетические профили, гоняет нагрузку и снова прячет их из поиска. Это не люди: почта `extra00001@load.talent`, имя «Профиль 00001», без телефона и даты рождения. Демо-аккаунты команда не удаляет. На 2000 профилях в поиске 1674, на 10 000 — 8497 (`python -m seed.generate_seed --extra-candidates N`, строка `in_search`).

Сценарий подборки: 20 работодателей, у каждого три потребности, страницы со смещением 0, 20 и 40, 60 секунд. Запросов больше 300, лимит 30 поисков в минуту не срабатывает.

До кеша на 10 000 профилях медиана подборки была 192 мс и 95-й перцентиль 1140 мс при двух процессах API (344 запроса) и 182 мс / 799 мс при четырёх (349 запросов). Оба 95-х перцентиля выше 500 мс, поэтому подборка кешируется. Кэш отдельных страниц на 60 секунд ускорил типичный ответ, холодный хвост оставил: на 10 000 и двух процессах медиана 115 мс, 95-й перцентиль 1120 мс. Таблица ниже — тот прогон.

Общий порядок в Redis на 300 секунд, карточки собираются только для запрошенной страницы. Команда на 10 000 профилях и двух процессах: `python tests/load_api.py --scenario shortlist --seconds 60 --reuse`. Напечатано: 367 запросов, 5,8 в секунду, ошибок 5xx нет, ответов 429 нет, медиана 18 мс, 95-й перцентиль 360 мс, 99-й 596 мс.
