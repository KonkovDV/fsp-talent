# Интеграция с реестром ФСП и ФСП ID

ТЗ не задаёт API и структуру данных ФСП: команда сама решает, что получать и как показывать (разделы 2 и 3.4). Ниже — предложение Федерации и то, что уже работает.

Короткий итог:

- **Вход через ФСП ID работает по OpenID Connect** — открытому стандарту входа через внешний сервис. Платформа — обычный клиент Keycloak (сервера учётных записей, на котором будет работать ФСП ID): вход по коду авторизации с защитой от перехвата кода (PKCE). В демо роль Keycloak играет помеченная страница этого сайта. Для подключения настоящего ФСП ID код менять не нужно, достаточно настроек в `.env`.
- **Из реестра берём только строки протокола:** соревнование, дисциплина, статус по ЕКП, место, число участников, командность, дата. Пол, контакты и документы не запрашиваем.
- **Результаты ФСП — отдельная ось профиля.** На грейд они не влияют. Кандидат без истории ФСП ничего не теряет: ось просто не учитывается (ТЗ 2.1).

## 1. Вход через ФСП ID (OpenID Connect, Keycloak)

ТЗ: «В дальнейшем ФСП ID будет работать на базе Keycloak, поэтому совместимость с этим решением упростит последующую интеграцию».

```mermaid
sequenceDiagram
    autonumber
    actor К as Кандидат
    participant П as ФСП Талант (frontend)
    participant A as ФСП Талант (API)
    participant ID as ФСП ID (Keycloak)
    participant Р as Реестр ФСП
    К->>П: «Войти через ФСП ID» в профиле
    П->>A: POST /candidates/me/fsp/authorize
    A->>A: state и code_verifier в Redis (10 минут, привязаны к кандидату)
    A-->>П: authorize_url с code_challenge (S256)
    П->>ID: переход на страницу входа ФСП ID
    К->>ID: имя пользователя и пароль ФСП (только здесь)
    ID-->>П: возврат на /candidate/fsp-callback?code&state
    П->>A: POST /candidates/me/fsp/callback {code, state}
    A->>ID: обмен кода на токены (client_secret + code_verifier)
    A->>ID: ключи realm (JWKS)
    A->>A: проверка подписи, iss, aud, exp, ФСП ID из утверждения fsp_id
    A->>Р: GET /participants/{fsp_id}
    Р-->>A: строки протокола
    A->>A: запись результатов, удостоверения VC, пересчёт оси ФСП
    A-->>П: {fsp_id, results}
```

Свойства, которые проверяют тесты `backend/tests/unit/test_fsp_identity.py`:

- пароль ФСП вводится только на странице провайдера, платформа его не видит;
- `state` одноразовый и принадлежит одному кандидату: чужой `state` отклоняется;
- код одноразовый и привязан к `code_challenge`: перехваченный код без `code_verifier` этой сессии бесполезен;
- код выдаётся только для зарегистрированного `client_id` и адреса возврата;
- ID-токен проверяется по ключам пространства Keycloak (realm): подпись, издатель, аудитория, срок. Токен для другого клиента, просроченный или подписанный чужим ключом отклоняется;
- вычисление `code_challenge` сверено с примером из RFC 7636.

### Режимы

| `FSP_ID_MODE` | Где вводят пароль | Что нужно |
|---|---|---|
| `mock` (демо) | Страница `/fsp-id/authorize` этого сайта с пометкой «Демо-провайдер». Реестр FSP2000–FSP2099, пароль `test` | Ничего |
| `oidc` | Страница входа Keycloak Федерации | `FSP_ID_ISSUER`, `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET`, `FSP_ID_CLAIM` |

### Что настроить в Keycloak Федерации

1. Клиент `fsp-talent`: Client authentication — On (конфиденциальный клиент), Standard flow — On, остальные потоки выключены.
2. Valid redirect URIs: `https://<адрес стенда>/candidate/fsp-callback` (привязка) и `https://<адрес стенда>/auth/fsp-callback` (вход).
3. Advanced → Proof Key for Code Exchange Code Challenge Method: `S256`.
4. Client scopes → mapper типа «User Attribute»: атрибут пользователя с номером ФСП ID → утверждение `fsp_id` в ID-токене.
5. В `.env` платформы: `FSP_ID_MODE=oidc`, `FSP_ID_ISSUER=https://<keycloak>/realms/<realm>`, `FSP_ID_CLIENT_ID=fsp-talent`, `FSP_ID_CLIENT_SECRET=<секрет клиента>`.

Код: `backend/app/services/fsp/identity.py` (`KeycloakFspIdProvider`, `MockFspIdProvider`), методы API — `backend/app/api/v1/candidates.py` (`/me/fsp/authorize`, `/me/fsp/callback`), демо-провайдер — `backend/app/api/v1/fsp_id_demo.py`.

### Вход в платформу через ФСП ID

Федерация ответила, что ФСП ID — единая точка входа, а вход на хакатоне можно имитировать. Поэтому ФСП ID работает двумя способами: привязка к готовому аккаунту (схема выше) и вход без регистрации по email. Регистрация по email (ТЗ 2.2, п. 4) остаётся.

```mermaid
sequenceDiagram
    autonumber
    actor К as Кандидат
    participant П as ФСП Талант (frontend)
    participant A as ФСП Талант (API)
    participant ID as ФСП ID (Keycloak)
    К->>П: «Войти через ФСП ID» на странице входа
    П->>A: POST /auth/fsp/authorize
    A-->>П: authorize_url (state не привязан к аккаунту)
    П->>ID: страница входа ФСП ID
    ID-->>П: возврат на /auth/fsp-callback?code&state
    П->>A: POST /auth/fsp/callback {code, state}
    alt ФСП ID уже привязан к аккаунту
        A-->>П: signed_in и токены
    else новый человек
        A-->>П: needs_consent, одноразовый билет (Redis, 15 минут) и данные реестра
        К->>П: согласия на обработку и условия
        П->>A: POST /auth/fsp/signup {ticket, consents}
        A-->>П: аккаунт из реестра, записи согласий, токены
    end
```

- Тот же поток кода с PKCE, что и привязка, но свой адрес возврата: `/auth/fsp-callback` (привязка — `/candidate/fsp-callback`). Код, выданный для одного адреса, другой поток не примет. `state` и код одноразовые.
- Без обязательных согласий (`terms`, `pd_candidate`) аккаунт не создаётся: 422 `consent_required`, билет не тратится. Повтор билета — 400 `fsp_ticket_invalid`.
- Такой аккаунт работает без email и пароля: личность подтверждает ФСП ID. Для связи кандидат добавляет Telegram или телефон в профиле, уведомления приходят в колокольчик.
- В Keycloak добавляется второй адрес возврата: `https://<адрес стенда>/auth/fsp-callback`.
- Как показать: «Вход» → «Войти через ФСП ID» → `FSP001` / `test` (аккаунт `fsp001@demo.talent` уже привязан, вход сразу) или любой из FSP2000–FSP2099 / `test` (новый человек, экран согласий).

Код: `backend/app/api/v1/auth.py` (`/fsp/authorize`, `/fsp/callback`, `/fsp/signup`), тесты — `backend/tests/unit/test_fsp_signin.py` (вход привязанного аккаунта, согласия до создания, одноразовые `state` и билет, разделение адресов возврата).

## 2. Контракт реестра ФСП

Предлагаемый контракт — один метод только на чтение. В режиме `FSP_MODE=real` его вызывает `HttpFSPAdapter` (`backend/app/services/fsp/registry.py`). В демо (`FSP_MODE=mock`) те же структуры отдаёт `MockFSPAdapter` с синтетическими протоколами.

```http
GET {FSP_API_URL}/participants/{fsp_id}
Authorization: Bearer {FSP_API_KEY}
Accept: application/json
```

```json
{
  "fsp_id": "FSP001",
  "display_name": "Иван Иванов",
  "region": "Томская область",
  "birth_date": "2003-05-12",
  "results": [
    {
      "event_id": "CR2025-ALG",
      "event_name": "Чемпионат России по спортивному программированию 2025",
      "discipline": "algorithmic",
      "competition_status": "russia_championship",
      "place": 3,
      "total_participants": 180,
      "regions_count": 52,
      "is_team": false,
      "team_size": 1,
      "role": "participant",
      "event_date": "2025-11-20",
      "protocol_url": "https://…"
    }
  ]
}
```

| Ответ | Что делает платформа |
|---|---|
| 200 | Записывает строки протокола, выдаёт по каждой подписанное удостоверение, пересчитывает ось ФСП |
| 404 | «Протоколы ФСП не найдены» (`fsp_not_found`), профиль остаётся без оси ФСП |
| другой код или неверная структура | 503 «Реестр ФСП сейчас не отвечает», ранее загруженные данные не трогаются |

Строка с неизвестной дисциплиной или местом вне `1…total_participants` пропускается, а не угадывается.

### Поля и зачем они нужны

| Поле | Зачем | Где используется |
|---|---|---|
| `discipline` | Одна из пяти дисциплин ВРВС «спортивное программирование» (`algorithmic`, `product`, `security`, `bas`, `robotics`) или `ai` — расширение вне ВРВС для протоколов соревнований по системам ИИ, загруженных вручную. Реестр Федерации `ai` не присылает: в ВРВС такой дисциплины нет ([fsp-russia.ru](https://fsp-russia.ru/), [Положение 2026](https://pravo.ppt.ru/polozheniye-polozheniya/330715)). Все соревнования весят одинаково, поэтому `ai` баллов не добавляет | Ось ФСП по дисциплинам, фильтр поиска |
| `competition_status` | Статус соревнования по ЕКП | Подпись строки протокола. В оценку не входит |
| `place`, `total_participants` | Класс результата: победитель, призёр, топ-10 %, верхняя половина, участие | Качество результата |
| `regions_count` | Показывается в карточке события, в оценку не входит | Карточка события |
| `ranks` | Разряд, дата присвоения и номер приказа по дисциплине | Профиль, фильтр «Разряд не ниже», PDF. В оценку не входит |
| `is_team`, `team_size` | Командный результат | Вес доказательства делится на √(размер команды): уверенность ниже, уровень не снижается |
| `event_date` | Давность | Затухание с полупериодом 18 месяцев |
| `birth_date` | Совершеннолетие | Профили младше 18 лет скрыты от работодателей без согласия законного представителя |
| `region` | Подпись в профиле | В балл подбора не входит |
| `display_name` | Подпись, если кандидат не указал имя сам | Видна работодателю только после согласия кандидата |

**Не запрашиваем:** пол, контакты, паспортные данные, место учёбы. Принцип минимизации из ст. 5 152-ФЗ: берём только то, что нужно для оценки.

Значения `competition_status`: `world`, `russia_championship`, `russia_cup`, `russia_youth`, `all_russian`, `federal_district`, `regional`, `other`.

### Аутентификация сервиса

В демо-контракте это ключ `Bearer`. В рабочей эксплуатации удобнее токен Keycloak по `client_credentials` того же клиента `fsp-talent` с отдельной ролью «чтение протоколов». Тогда доступ к реестру отзывается в одном месте вместе с входом.

## 3. Обновление данных

Протоколы загружаются при привязке ФСП ID. Повторно их забирает почасовая задача `sync_fsp_changes`: она спрашивает реестр, кто изменился после сохранённой отметки, и дописывает только новые строки уже привязанным участникам.

```http
GET {FSP_API_URL}/participants/changes?since=2026-10-01T00:00:00Z
→ {"fsp_ids": ["FSP001", "FSP017"], "next_since": "2026-10-06T12:00:00Z"}
```

Отметку хранит Redis (`fsp:changes:since`). Первый запуск смотрит на два часа назад. Повтор той же строки безопасен: пара (участник, соревнование) в таблице `results` уникальна, уже лежащая строка не пишется второй раз. В демо ту же выборку отдаёт `MockFSPAdapter`. Если Федерации удобнее самой присылать изменения, подойдёт вебхук (уведомление на наш адрес) «протокол утверждён» с той же структурой и подписью HMAC.

**Исправления и аннулирования.** Для изменившегося участника строки с `trust_level = verified_fsp` сверяются с ответом реестра по `event_id`. Строка, которой больше нет в реестре, удаляется (аннулирован протокол). Строка, у которой изменились место, размер поля, команда, дата, роль или дисциплина, заменяется исправленной. Подписанное достижение (VC) удалённой или заменённой строки отзывается (`revoked_at`), профиль пересчитывается. Протоколы, загруженные кандидатом из файла, не трогаются. Пустой ответ реестра ничего не удаляет, как и ответ, после которого пропало бы больше половины строк профиля (и больше одной): такой ответ считается неполным, в журнал пишется предупреждение, исправления мест при этом применяются. Сбой или обрезанная страница не должны стирать историю.

**Затухание пересчитывается каждую ночь.** Давность считается от даты расчёта, поэтому задача `rescore_fsp_nightly` (03:20 МСК) пересобирает профили, у которых оценка ФСП старше 20 часов или посчитана прежней версией методики. Иначе двух кандидатов сравнивали бы по разным опорным датам.

## 4. Как результат становится доказательством

1. Строка протокола → класс результата по месту и размеру поля (`result_class`, методика `v4.1.0`): победитель 1,00 · призёр (2–3 место) 0,85 · топ-10 % 0,65 · верхняя половина 0,45 · участие 0. Победитель и призёр — при шести участниках и больше. В нижнюю границу входит лучшее подмножество до пяти результатов. Статус соревнования не учитывается: по совету Федерации все соревнования одинаково важны. Разряд из этой строки не считается.
2. Вес результата = затухание с полупериодом 18 месяцев / √(размер команды) · (1 − e^(−N/30)), N — размер поля. За календарный месяц в пул идут не больше двух результатов дисциплины. Вклад внутри команды не разделяется: команда снижает уверенность, а не уровень.
3. По дисциплине — байесовское сжатие к среднему: у человека с короткой историей оценка ближе к средней. Затем берётся осторожная нижняя граница уровня (LCB, lower confidence bound), чтобы один удачный старт не выглядел как стабильный уровень. В подборке по потребности эта граница берётся по профильной дисциплине целиком, а по остальным — с весом 0,5 (`app/services/fsp/relevance.py`). Фильтр «дисциплина» оставляет одну дисциплину. Статус соревнования в выборе не участвует. Один случайный успех не обгоняет стабильную серию. Участие весит 0 и в балл не входит: оно остаётся в профиле, но оценку не поднимает и не опускает. Профиль нельзя набрать одними онлайн-участиями. Проверка — `python -m app.validation.fsp_axis --seeds 3` из каталога `backend`: 2000 человек, зёрна 2026, 2027 и 2028, место в протоколе зависит от скрытой силы, а число онлайн-участий в нижней половине — нет. Считается тот же движок оси, что работает в продукте. В корреляцию не входят люди без единой строки протокола. Корреляция Спирмена показывает, насколько порядок людей по показателю совпадает с порядком по скрытой силе (1 — полностью).

| Зерно | В корреляции | Спирмен LCB | Спирмен среднего места | Спирмен числа строк |
|---|---|---|---|---|
| 2026 | 1969 | 0,768 | 0,695 | 0,148 |
| 2027 | 1966 | 0,766 | 0,668 | 0,144 |
| 2028 | 1966 | 0,769 | 0,680 | 0,089 |
| среднее ± стандартное отклонение | | 0,768 ± 0,002 | 0,681 ± 0,014 | 0,127 ± 0,033 |

На каждом зерне LCB выше среднего места, а среднее место выше числа строк. Среднее место — средняя доля поля, которую человек оставил позади (выше значит финиш лучше). Накрутка из 40 онлайн-участий в нижней половине даёт LCB 0,16 (как пустая история), две победы — LCB 0,54. Грейд эта проверка не трогает.
4. Ось ФСП влияет на место кандидата внутри категории и никогда — на грейд: грейд даёт только тест специализации. Разряд — факт реестра (разряд, дата, приказ), а не расчёт по месту. Он показывается в профиле и фильтре «Разряд не ниже» и в оценку не входит. Формулы балла — в [README](../README.md#ось-подтверждено-фсп) и `backend/app/services/scoring/engine.py`, версия `v4.1.0`: новое событие никогда не опускает нижнюю границу.

## ЕВСК 2026–2029

Действующий документ — приказ Минспорта России от 09.04.2026 № 299 «Об утверждении Единой всероссийской спортивной классификации», зарегистрирован Минюстом 05.06.2026 № 86925, вступил в силу 19.06.2026. Нормы по спортивному программированию — приложение № 77 (пункт 1.77). Прежний приказ от 11.01.2022 № 6 утратил силу.

Разряды присваиваются по нормам приложения № 77 к приказу № 299; платформа получает разряд из реестра ФСП готовым фактом и сама не вычисляет. Демо-реестр стенда выдаёт демо-разряды по своей таблице (`_DEMO_RANK_TABLE` в `backend/app/services/fsp/mock.py`), номер приказа начинается с `Приказ-демо-`: это демонстрационная запись, не приказ органа власти. Срок действия разряда в балл не входит.

В вид спорта «спортивное программирование» во Всероссийском реестре видов спорта входят пять дисциплин: алгоритмическое, продуктовое, беспилотных авиационных систем, робототехники и систем информационной безопасности (приказ Минспорта России от 31.01.2023 № 58; те же пять дисциплин — в федеральном стандарте спортивной подготовки, приказ от 24.06.2025 № 445). Код `ai` («программирование систем ИИ») — направление календаря ЕКП 2026, а не дисциплина ВРВС; в подборе он относится к специализации ML (`backend/app/services/categorization.py`). Подпись «вне ЕВСК» не ставится.

5. По каждой строке выдаётся удостоверение W3C Verifiable Credentials 2.0 (`eddsa-jcs-2022`). Любой может проверить подпись: `GET /api/v1/public/issuer`, `POST /api/v1/public/credentials/verify`.

Сейчас издатель удостоверений — платформа: она подтверждает, что результат получен из системы ФСП. В рабочей эксплуатации издателем может стать сама Федерация со своим ключом, формат при этом не меняется.

## 5. Что видит работодатель

Карточка в выдаче анонимна: статус соревнования, год и диапазон процентиля («топ-5 %»). Названия события и точного места в ней нет, чтобы по ним нельзя было найти человека в открытом протоколе. После того как кандидат принял приглашение или откликнулся сам, работодатель видит имя и контакты. Каждый просмотр записывается в журнал доступа.
