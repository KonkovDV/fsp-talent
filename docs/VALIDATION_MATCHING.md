# Проверка подбора кандидатов

Механика подбора даёт 35 % оценки решения. Качество подбора проверено на синтетическом наборе со **скрытой правдой**: подбор видит только зашумлённые наблюдения, как в жизни, а релевантность считается по правде. Код проверки: `backend/app/validation/matching.py`. Ранжирует та же функция `app.services.matching.score`, что работает в API.

## Как устроена оценка соответствия

- Попадание в список решает соответствие потребности: навыки 0,50, грейд 0,20, специализация 0,20, текст 0,05, сфера 0,05.
- Навык засчитывается с весом доказательства: подтверждён тестом 1,0, цитатой из резюме 0,75, заявлен 0,55. Близкая технология (MySQL вместо PostgreSQL) даёт частичный зачёт 0,3.
- Грейд: точное совпадение 1,0, на ступень выше 0,6, на ступень ниже 0,35; грейд без подтверждения тестом умножается на 0,85.
- Среди кандидатов с одинаковым соответствием (до сотой) порядок задают тест (0,62) и протокол ФСП (0,38). Они сдвигают оценку меньше чем на 0,01 и не поднимают человека с худшим совпадением навыков.
- Неприменимый фактор не учитывается, веса остальных нормируются. Если в потребности нет сферы или у кандидата нет истории ФСП, этот фактор просто выпадает, и кандидат не теряет баллы (ТЗ 2.1).
- Каждый фактор оставляет в карточке строку «плюс / минус / инфо», работодатель видит и сами веса.
- Для потребности дополнительно подбираются **рекомендуемые категории**: ячейки «специализация × грейд» с самыми сильными совпадениями.

## Синтетический набор

Кандидат: специализация, способность θ ~ N(0, 1), реальные навыки. Наблюдения искажены так, как это бывает в анкетах: заявленные навыки теряют 25 % реальных и добавляют около 15 % ложных; 30 % заявленных навыков подтверждены цитатой; заявленный грейд у 30 % кандидатов на ступень выше реального и у 10 % ниже; тест проходят 45 %, он подтверждает реальные навыки и уровень; у 55 % есть история ФСП с LCB, связанной с θ.

Релевантность (0–3) считается только по правде: 3 — та же специализация, все обязательные навыки реальны, грейд совпадает; 2 — специализация та же или смежная, навыки реальны, грейд отличается не больше чем на ступень; 1 — реальна хотя бы половина навыков; 0 — иначе.

## Результаты

Специализации в наборе — все одиннадцать направлений продукта. Релевантность считается по скрытым навыкам и грейду и не смотрит на формулу оценки.

### Набор с зерном 2026

Команда: `python -m app.validation.matching`. 800 кандидатов, 78 потребностей с релевантными кандидатами, SHA-256 `2801aecbd26d42806134c4f11f73057ea0b2a0ea5acd5f80de5f1ae88f49ceef`.

| Ранжирование | nDCG@10 | P@10 (оценка ≥ 2) | MAP |
|---|---|---|---|
| Случайный порядок | 0.034 | 0.035 | 0.043 |
| Базовая линия: совпадение заявленных навыков | 0.615 | 0.565 | 0.548 |
| ФСП Талант: оценка соответствия | 0.660 | 0.663 | 0.618 |
|   без весов доверия к навыкам | 0.658 | 0.677 | 0.606 |
|   без теста | 0.661 | 0.668 | 0.625 |
|   без оси ФСП | 0.661 | 0.664 | 0.619 |

## Выводы

- Подбор обходит поиск по ключевым словам на обоих наборах: nDCG@10 выше на 0,045 и 0,089, MAP — на 0,070 и 0,108.
- Веса доверия к навыкам на зерне 7 поднимают nDCG@10 с 0,675 до 0,715. На зерне 2026 разница 0,002: заявленные навыки уже хорошо разделяют этот набор.
- Тест и ось ФСП уточняют порядок среди одинакового соответствия и не обязаны поднимать nDCG. На зерне 2026 nDCG@10 равен 0,660 с осью ФСП и 0,661 без неё. На зерне 7 обе цифры равны 0,715. Кандидат без истории ФСП из-за этого не теряет баллы. Ось ФСП в симуляции задана сразу нижней границей LCB, поэтому методика `v3.0.0` эти таблицы не переписывает.
- `--check` требует, чтобы полная оценка была выше и ключевых слов, и случайного порядка по nDCG@10. Эта проверка стоит в CI.

## Разметка жюри

Своих пар у хакатона нет. Файл для жюри — JSONL, одна пара на строку: потребность, наблюдаемый профиль кандидата и оценка 0…3. Оценки независимы от формулы. Команда из каталога репозитория:

```bash
cd backend && python -m app.validation.matching --pairs ../docs/examples/jury_pairs.jsonl
```

Она печатает nDCG@10, P@10 и MAP. Три строки примера:

```json
{"need": {"id": "n1", "role": "backend", "grade": "middle", "skills": ["Python", "PostgreSQL"]}, "candidate_id": "c1", "candidate": {"observed": {"role": "backend", "grade": "middle", "grade_source": "assessed", "skills": {"Python": "test_confirmed", "PostgreSQL": "test_confirmed"}, "test_p": 0.9, "fsp_lcb": 0.6, "industry": "fintech"}}, "label": 3}
{"need": {"id": "n1", "role": "backend", "grade": "middle", "skills": ["Python", "PostgreSQL"]}, "candidate_id": "c2", "candidate": {"observed": {"role": "backend", "grade": "junior", "grade_source": "declared", "skills": {"Python": "self_reported"}, "test_p": null, "fsp_lcb": null, "industry": "fintech"}}, "label": 1}
{"need": {"id": "n1", "role": "backend", "grade": "middle", "skills": ["Python", "PostgreSQL"]}, "candidate_id": "c3", "candidate": {"observed": {"role": "ml", "grade": "senior", "grade_source": "declared", "skills": {"Python": "self_reported"}, "test_p": null, "fsp_lcb": 0.4, "industry": "fintech"}}, "label": 0}
```

Тот же расчёт принимает JSON в формате `--export`: `python -m app.validation.matching --import pairs.json`.
