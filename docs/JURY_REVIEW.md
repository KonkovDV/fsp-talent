## 0. Краткий вердикт

Сильный инженерный прототип с редкой для хакатона методологической дисциплиной: явная статистическая модель уровня, гибридный поиск с RRF, криптографически подписанные результаты, журналы согласий. Главный риск не в коде, а в **соответствии задаче**: публичная формулировка кейса говорит о платформе «поиска и подбора ИТ-вакансий» и сопоставлении их с профилем соискателя, а решение реализует только обратный найм (работодатель → кандидат). Сущности «вакансия» и сценария «кандидат ищет вакансии» нет.

## 2. Соответствие задаче и «боль»

**Боль.** Junior-сегмент перегрет: по данным hh.ru, в январе–августе 2025 на одну junior-вакансию разработчика приходилось 18,6 резюме против 9,8 годом раньше ([Коммерсантъ](https://www.kommersant.ru/doc/8025417)). Работодателю не хватает проверяемого сигнала навыка; у кандидата с разрядом ФСП этот сигнал есть, но в резюме он не читается и не верифицируется. Решение точно бьёт в эту асимметрию информации (signaling, Spence 1973): результат из протокола → оценка с неопределённостью → подписанное удостоверение.

**Разрыв с формулировкой.** Кейс сформулирован со стороны соискателя («поиск ИТ-вакансий», «сопоставление с профилем»). В репозитории нет модели `Vacancy`, нет страницы вакансий у кандидата, оффер выступает одноразовой персональной «вакансией». Эксперт с высокой вероятностью снизит «соответствие». Минимальная доработка, которая закрывает разрыв без переделки архитектуры:

1. `vacancies` (employer_id, role, grade, дисциплина, min_rank, skills[], вилка, формат, флаг «допускается 16–17 лет»), индекс той же моделью `skills_tsv` + trigram.
2. `GET /candidates/me/vacancies`: тот же пайплайн в обратную сторону (жёсткие фильтры → покрытие навыков → RRF), с тем же блоком `why`/`missing_skills` — это и есть «сопоставление с профилем».
3. Оффер ссылается на `vacancy_id` (nullable), отклик кандидата создаёт зеркальную запись. Двусторонний рынок = та же таблица с полем `initiator`.
4. В питче позиционировать обратный найм как дифференциатор поверх базового мэтчинга, а не вместо него.

**Конкурентное поле.** hh.ru / Хабр Карьера (массовый поиск, самодекларация навыков), getmatch (персональный мэтчинг), Яндекс Контест и Codeforces (рейтинг без рынка труда), Hired/TalentReverse (анонимный обратный найм). Уникальная позиция проекта: единственный источник навыка, подтверждённый официальными протоколами общероссийской спортивной федерации, с анонимностью до согласия.

## 3. Модель оценки v2.0.0: разбор

Формулы из README реализованы в `backend/app/services/scoring/engine.py` дословно.

**3.1. Интерпретация.** Оценка — это точный апостериор нормально-нормальной конъюгатной модели с **известной** дисперсией наблюдения τ² = 0,04 и априорным N(μ0 = 0,30, τ²/K = 0,02), где веса w играют роль дробных псевдонаблюдений (power prior, Ibrahim & Chen 2000):

```
q_i | θ ~ N(θ, τ² / w_i),   θ ~ N(μ0, τ² / K)
⇒ E[θ | q] = (Σ w q + K μ0) / (Σ w + K),   Var[θ | q] = τ² / (Σ w + K)
```

Из этого следует, что название «байесовский» корректно, но условно: σ не зависит от разброса наблюдений. Участник с результатами {0,95; 0,05} получит тот же σ, что и {0,50; 0,50}. Рекомендация: либо задокументировать допущение гомоскедастичности, либо перейти к Normal-Inverse-Gamma (τ² оценивается) или к эмпирическому Байесу (μ0, K из всей популяции по дисциплине).

**3.2. LCB.** `μ − σ` — односторонняя граница ≈ 84 %. Для справедливости к новичкам это разумный выбор (ср. Evan Miller, «How Not To Sort By Average Rating»), но z стоит вынести в конфиг и назвать уровень в UI («с вероятностью ≈ 84 % уровень не ниже…»).

**3.3. Двойной учёт места.** `q = W(разряд) · p`, но разряд-эквивалент сам выводится из (статус, место, N). Место входит в q дважды, и в точках смены разряда q имеет скачок. Чище: `q = S(статус) · p`, где S — вес уровня соревнования, а разряд-эквивалент оставить как отдельный объяснимый фильтр.

**3.4. Команды.** `1/√(размер)` — эвристика без идентификации вклада. При наличии истории разных составов индивидуальный вклад идентифицируем через TrueSkill (Herbrich et al., NIPS 2006). Для прототипа допустимо, но в документации стоит назвать это эвристикой.

**3.5. Калибровка.** Все гиперпараметры (K = 2, μ0 = 0,30, τ² = 0,04, полураспад 18 мес.) экспертные. На реальных протоколах ФСП их можно проверить прогнозной валидностью: оценка на момент t → ранговая корреляция (Kendall τ) с местом на следующем соревновании, покрытие интервала (доля случаев, где следующий q выше LCB, должна быть ≈ 0,84). Синтетический генератор уже имеет латентный `skill`, так что эту проверку можно сделать прямо сейчас (recovery test: Spearman ρ между `skill` и LCB).

**3.6. Процентиль Хазена** `1 − (place − 0,5)/N` корректен и несмещён для равномерного распределения мест. При малых N он даёт высокие значения (1-е из 3 → 0,83); порог «МС/КМС не менее 6 участников» частично это компенсирует, но сам q остаётся завышенным. Вариант: умножать w на `min(1, N/N0)`.

## 4. Поиск

- Жёсткие фильтры в SQL → лексический ранг (`ts_rank` + `similarity`) → опционально pgvector → RRF (K = 60, Cormack et al., SIGIR 2009). Реализация соответствует README.
- **Исправлено в этой ветке:** при выбранной дисциплине сигнал качества брался как max LCB по всем дисциплинам, и сильный алгоритмист поднимался в поиске по ИБ.
- LCB учитывается дважды: как ранжирование внутри RRF и как tie-break. Это осознанное смещение к «подтверждённым» кандидатам, его стоит назвать в README.
- `total` — размер пула (≤ 1000), а не COUNT(*). Добавлен флаг `pool_capped`.
- Нет офлайн-оценки. Предложение: 30–50 синтетических запросов работодателя с разметкой релевантности → nDCG@10, Recall@20 для lex / lex+quality / +dense; это закрывает критерий «эффективность».
- Карточка псевдонимна, а не анонимна: стабильный `candidate_id` + регион + стаж + год и статус события для редких дисциплин (БАС, робототехника) сопоставимы с публичными протоколами. Рекомендуется k-анонимность по квази-идентификаторам (Sweeney 2002): скрывать регион/год, если комбинация встречается реже k = 5 раз, и выдавать работодателю пер-работодательский псевдоним (HMAC(employer_id, participant_id)).

### 5.2. Осталось (не трогали, чтобы не ломать демо)

- JWT в `localStorage` (Zustand persist); refresh-токен выдаётся, но эндпоинта refresh нет. Целевая схема: HttpOnly/Secure/SameSite cookie для refresh + короткий access в памяти.
- Нет rate limit на логин, поиск и `/ai/*` (Redis уже есть — хватит token bucket).
- `is_minor` считается только при регистрации и устаревает; лучше вычислять из `birth_date` в запросе или пересчитывать задачей beat раз в сутки.
- `_jcs()` — детерминированный `json.dumps(sort_keys=True)`, а не полный RFC 8785 (сериализация чисел в стиле ECMAScript, сортировка по UTF-16). Сейчас в удостоверениях только целые числа и ASCII-ключи, поэтому результат совпадает, но заявлять интероперабельность можно только после прогона тест-векторов W3C vc-di-eddsa.
- Нет статуса отзыва (Bitstring Status List) и ротации ключа: потеря тома `vc_keys` делает все выданные удостоверения непроверяемыми.
- `GET /public/credentials/{id}` отдаёт точное событие и место — для открытого профиля это допустимо, но должно быть частью отдельного согласия на распространение (ст. 10.1 152-ФЗ).
- CI-деплой собирает образы, но не публикует их, а на хосте делает `docker compose pull` без `image:` — деплоится не то, что собрано. `smoke_api.py` в CI не запускается.

### 5.3. Правовая рамка (РФ)

- **152-ФЗ, ст. 9** (ред. с 01.09.2025): согласие оформляется отдельно от иных документов. Нужны раздельные согласия: обработка профиля; передача контактов конкретному работодателю (уже есть: принятие оффера); публичная страница.
- **Ст. 10.1** (данные, разрешённые для распространения): лидерборд и публичный профиль требуют отдельного согласия с выбором категорий.
- **Ст. 18 ч. 5**: локализация. Резюме во внешний LLM — только российский (GigaChat подходит) и после вырезания ПДн.
- **Несовершеннолетние 16–17 лет** (ЛЦТ допускает 16+): ТК РФ ст. 63, 92 (≤ 35 ч/нед), 265, 268. Карточка кандидата 16–17 должна предупреждать работодателя об ограничениях, а оффер — требовать подтверждения соответствия условий. Согласие законного представителя — отдельный поток (ссылка-приглашение на email родителя, идентификация, журнал), а не флажок в аккаунте ребёнка.
- **W3C VC в РФ** не имеет юридического статуса; корректная формулировка в README («издатель — платформа, не ФСП») верная. Для продакшена: издатель — ФСП, ключ в HSM, опционально ГОСТ Р 34.10-2012 рядом с Ed25519.
