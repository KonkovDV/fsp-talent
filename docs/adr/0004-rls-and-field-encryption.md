# 0004. RLS в PostgreSQL и AES-256-GCM для контактов

**Контекст.** Ошибка в одном запросе API не должна открывать чужое резюме или контакты. Утечка дампа базы не должна раскрывать телефоны и почту кандидатов (152-ФЗ).

**Решение.** Приложение работает от роли `fsp_app`; таблицы с данными кандидата под `FORCE ROW LEVEL SECURITY`, и политика пропускает строку только владельцу из переменной сессии `app.participant_id`, работодателю на чтение в поиске или явному служебному флагу (`backend/alembic/versions/0001_initial.py`, политики `*_owner`). Контактные поля шифруются AES-256-GCM, связанные данные — таблица, колонка и строка, поэтому шифртекст нельзя перенести на другого человека; вход ищет не по шифртексту, а по отдельному HMAC (`backend/app/services/field_cipher.py`).

**Альтернативы.** Проверки только в коде API — одна забытая проверка открывает данные. Шифрование всего диска — не защищает от дампа через приложение. pgcrypto в базе — ключ попадает в SQL и журналы.

**Последствия.** Каждый запрос выставляет контекст сессии; миграции идут отдельной ролью (`MIGRATE_DATABASE_URL`). Поиск по контактам невозможен, кроме точного совпадения по HMAC. Ключ шифрования — `FIELD_ENCRYPTION_KEY` или, если он пуст, производный от ключа подписи (`backend/app/core/config.py`); его потеря означает потерю контактов, поэтому ключи входят в резервную копию ([INSTALL.md, 11.6](../INSTALL.md#116-резервные-копии-и-восстановление)).
