| # | Дефект | Доказательство | Следствие |
|---|---|---|---|
| 1 | `backend/app/services/assessment.py` — однострочный base64 (14,5 КБ), с 7297-го символа испорчен посторонней `(` | Коммит `97ff3e9`, 05.10 01:05. `python -c "import app.main"` → `SyntaxError` | `app.api.v1.router` не импортируется, API не стартует |

| 3 | `0008`: `down_revision = "0007"`, а id ревизии 0007 — `"0007_result_participant_event"` | `alembic upgrade head` → `KeyError: '0007'` | `CMD` контейнера (`alembic upgrade head && uvicorn …`) падает до старта API |

**Корневая причина.** Оба файла записаны инструментом, который сам кодирует содержимое в base64 и коммитит напрямую в `main`: блоб `assessment.py` корректен первые ~7,3 КБ, дальше декодируется в мусор. CI на этих коммитах был бы красным (`ruff` видит `invalid-syntax`, `tsc` видит `TS1109`), но ветка `main` не защищена, и красный CI ничего не блокирует. Восстановление: `authStore.ts` декодирован целиком и доработан; `assessment.py` восстановить нельзя, модуль написан заново по замыслу из docstring и предыдущей версии.

**Что сделано, чтобы не повторилось** (`backend/tests/unit/test_repo_integrity.py`, все три проверки падают на `origin/main` и проходят на ветке):
- ни один исходный файл не является однострочным base64 (порог 99 % символов алфавита, ловит и испорченный блоб);
- каждый модуль `app.*` импортируется;
- у Alembic один head и нет висячих родителей.

CI дополнительно поднимает PostgreSQL, применяет миграции, засевает данные и гоняет `tests/smoke_api.py` против живого `uvicorn`. **Нужно действие владельца репозитория**: включить защиту `main` с обязательными проверками CI (Settings → Branches или Rules). Для приватного репозитория защита веток доступна на GitHub Pro или Team; на бесплатном тарифе остаётся дисциплина «только через PR с зелёным CI». Без этого любой следующий прямой коммит снова может уронить стенд в период экспертизы.

### 3.2. Попов: «Даёт ли тест стабильный грейд при повторе?» (прямо в критерии 2)
Процедура: `python -m app.validation.assessment`. Это симуляция с восстановлением параметров: 4000 кандидатов с известной способностью θ ~ N(0,3; 1) заявляют свой истинный грейд и дважды проходят тест на реальном банке. Ответы генерируются по модели 2PL, расчёт идёт через функции сервиса.

| Метрика | Значение |
|---|---|
| Вопросов в сессии (junior / middle / senior / lead) | 14 / 15 / 13 / 8 |
| Медианная погрешность θ (SE) | 0,50 при ширине полосы грейда 1,0 |
| Повтор: тот же исход «сдал / не сдал» | 74 % |
| Повтор: тот же точный грейд | 69 % (было 55 % без запаса 1·SE) |
| Ложные повышения выше истинного грейда | 1,6 % (было 13 %) |
| Доля верных ответов: слабая / сильная четверть | 29 % / 77 % |

**Слабое место.** Это верхняя граница: в симуляции ответы следуют модели, а в жизни добавятся угадывание, плохо откалиброванные задания и утечка. Те же расчёты показывают, что даже с идеально откалиброванными заданиями 15 вопросов дают ~72 % совпадения «сдал / не сдал», а 30 и 45 вопросов — 79 % и 81–83 %. Значит, длину теста определяет требуемая стабильность, а не удобство.

### 3.3. Попов: «Как сделать задания устойчивыми к утечке без LLM-генерации на лету?»
ТЗ прямо отвергает оба крайних варианта: общий набор утекает, генерация нейросетью под каждого не гарантирует сопоставимой сложности. Предлагаемый подход:
- **Семейства заданий из шаблонов.** Шаблон с параметрами (данные, константы, фрагмент кода, порядок и формулировка вариантов) даёт тысячи изоморфных экземпляров одной трудности. Калибруется трудность семейства, а не экземпляра, поэтому сложность сопоставима, а выученный ответ не переносится.
- **Адаптивный тест на классификацию.** Следующее задание выбирается вблизи порога заявленного грейда; тест останавливается, когда θ ± SE целиком по одну сторону порога (последовательная классификация). Это даёт ту же стабильность при меньшем числе заданий.
- **Контроль экспозиции.** Ограничить долю показов каждого семейства (метод Sympson–Hetter) и не повторять семейства одному кандидату.
- **LLM** — только для черновиков шаблонов с ревью человеком и пилотной калибровкой, а не для заданий в рантайме.
- **Калибровка** параметров a и b по реальным ответам (маргинальное правдоподобие / EM) после ~200 ответов на семейство; до этого — экспертные априоры и симуляция из 3.2.

### 3.7. Лючева: «Почему МС без теста стоит ниже кандидата с III разрядом и тестом?»
Это две разные оси. Грейд — рабочая квалификация, по ТЗ подтверждается тестом. Разряд — спортивный уровень, подтверждённый протоколами ФСП. ТЗ требует строить выдачу по категориям из теста. МС виден на карточке и через фильтр разряда, а тест он может пройти за полчаса. **Сделать до защиты:** пояснение этой логики в интерфейсе поиска.

### 3.8. Лючева: «Что кандидат видит до начала общения?»
Компанию, роль, формат, вилку «от–до» в рублях, сообщение и способ связи с компанией. Контакты кандидата работодатель видит только после принятия приглашения или отклика; раскрытие пишется в журнал.

### 3.9. Лючева: «Не дискриминация ли фильтры по разряду и скрытие несовершеннолетних?»
Несовершеннолетние скрыты до согласия законного представителя: это защита, а не отбор. Разряд и подтверждённый грейд — деловые качества. Формулировки фильтров стоит проверить с юристом на соответствие ст. 64 ТК РФ.

### 3.10. Лючева: «Пустой рынок: зачем работодателю приходить?»
Стартовая ликвидность — база участников ФСП с уже подтверждёнными результатами. Для кандидата ценность в приглашениях с зарплатой до начала общения. Без входа для кандидатов вне ФСП (1.4, п.2) рынок ограничен этой базой.
