# Сборка, развёртывание и локальный запуск

Инструкция для эксперта, который разворачивает решение на своей машине, и для оператора сервера (ТЗ 3.3, 3.4). Разделы 1–10 — локальный запуск, раздел 11 — продуктивная установка с HTTPS, резервными копиями, обновлением и откатом. Тот же путь, что в разделах 3–4, описан в `.github/workflows/ci.yml` (задание `compose-e2e`: `make demo` и `make check` на чистой машине).

Время первого запуска — 5–10 минут: столько уходит на сборку образов. Повторный запуск занимает меньше минуты.

## 1. Что понадобится

| Что | Версия | Как проверить |
|---|---|---|
| Docker Engine или Docker Desktop | 24 и новее | `docker --version` |
| Docker Compose v2 | 2.17 и новее (нужен флаг `--wait`) | `docker compose version` |
| Git | любая | `git --version` |
| Свободная память | 4 ГБ | всё вместе занимает около 1,5 ГБ |
| Место на диске | 5 ГБ | образы и зависимости |
| Свободные порты | 80 и 8025 | порт 80 можно поменять, см. раздел 9 |

`make` нужен только для коротких команд. В Windows его обычно нет, поэтому для PowerShell рядом даны те же команды без `make`.

Подходит Linux, macOS (Intel и Apple Silicon) и Windows 10/11 с Docker Desktop на WSL 2. Python и Node.js на машине не нужны: всё собирается внутри контейнеров.

Машина проверки жюри (32–64 ГБ памяти, около 8 ядер, без видеокарты) подходит с запасом: видеокарта решению не нужна.

## 2. Получить код

```bash
git clone https://github.com/KonkovDV/fsp-talent.git
cd fsp-talent
```

Если код пришёл архивом, распакуйте его и откройте терминал в папке `fsp-talent`.

## 3. Запустить одной командой

**Linux и macOS**

```bash
make demo
```

**Windows (PowerShell)**

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
docker compose up -d --build --wait
docker compose exec -T -u appuser backend python -m seed.generate_seed
```

Тот же запуск без набора команд: в папке проекта выполните `powershell -ExecutionPolicy Bypass -File scripts\start-local.ps1`. Скрипт сам создаст `.env`, дождётся контейнеров и загрузит демо-данные. Повторный запуск безопасен.

Письмо с кодом подтверждения на этом запуске не приходит в Gmail и на другую почту. Откройте http://localhost:8025: это локальный ящик Mailpit. Своя почта нужна только стенду жюри и задаётся в `deploy/.env` (`SMTP_HOST` и соседние поля).

`make demo` выполняет те же три шага:

1. Создаёт `.env` из `.env.example`, если файла ещё нет. Править его не нужно. Ключ подписи токенов контейнер сам создаст при первом старте и сохранит в томе `vc_keys`.
2. Собирает образы, поднимает контейнеры и ждёт, пока база, backend, worker, beat и frontend станут `healthy`. Миграции базы применяются при старте backend.
3. Загружает демо-данные. Повторный запуск безопасен: уже загруженное не дублируется.

В конце команда печатает адреса и демо-входы.

## 4. Проверить, что всё работает

| Адрес | Что там |
|---|---|
| http://localhost | Сайт: кабинеты кандидата и работодателя |
| http://localhost/docs | Swagger UI: все методы API с запросами, ответами и кодами ошибок |
| http://localhost/openapi.json | Спецификация OpenAPI 3.1 |
| http://localhost/health | `{"status":"ok",...,"build":"<sha коммита>"}`: `build` — коммит сборки (`make demo` передаёт `git rev-parse HEAD`; без git — `unknown`) |
| http://localhost:8025 | Mailpit: письма с кодами подтверждения и уведомлениями |

Команда `docker compose ps` должна показать девять контейнеров в состоянии `running`: nginx, frontend, backend, worker, beat, postgres, redis, mailpit и sandbox. Sandbox запускает решения задач с кодом, сети у него нет. Проверка здоровья есть у базы, backend, worker, beat, frontend и sandbox. У redis, Mailpit и nginx её нет. Keycloak стартует отдельно, с профилем `fsp-id`.

Сквозная проверка API на запущенном стенде:

```bash
make check
```

Команда регистрирует нового кандидата (код подтверждения она берёт из Mailpit), привязывает ФСП ID через демо-провайдера, проходит адаптивный тест, ищет кандидата, отправляет приглашение и проверяет раскрытие контактов. Она же проверяет задания от работодателя (с проверкой системой и работодателем), вход через ФСП ID привязанного и нового кандидата, переписку по принятому приглашению и закрытие контактов для одной компании. Она же проверяет аккаунты жюри, согласие законного представителя и обходит все маршруты с идентификатором объекта: другой работодатель и другой кандидат не получают чужих объектов. Успешный прогон заканчивается строкой `SMOKE OK`.

> `make check` меняет демо-данные: например, подтверждает тестом грейд кандидата `fsp001@demo.talent`. Чтобы вернуть стенд к исходному виду, выполните `make reset` и снова `make demo`.

Пошаговый сценарий из ТЗ 3.3 и описание всех экранов — в [руководстве пользователя](USER_GUIDE.md). Ниже два разных прохода: короткий показ и самостоятельная проверка.

### Показ за три минуты

За десять минут до показа стенд уже поднят (`make demo`). Стенд жюри каждую ночь в 04:10 МСК возвращается в исходное состояние: `make demo-reset`. После сброса у `jury1@demo.talent`…`jury10@demo.talent` пустой опрос и нет ни одного теста: ни пробного, ни полного. Подтверждённый грейд появится, только если перед показом пройти опрос и полный тест под `jury1@demo.talent` (backend, middle). Во второй вкладке вошёл `hr@sibcode.demo`, в третьей — `fsp001@demo.talent`. Пароль у всех `demo12345`. В одной вкладке включена тёмная тема. Если показ сокращают до двух минут, строку 0:20–0:50 пропускают.

| Время | Кто | Что сделать | Что сказать |
|---|---|---|---|
| 0:00–0:20 | — | Слайд «Ответ» | Работодатель находит человека, а не наоборот. Грейд даёт только тест, ФСП — отдельная подтверждённая ось, контакты — после согласия. |
| 0:20–0:50 | Кандидат | Вход → «Войти через ФСП ID» → `FSP001` / `test` → «Результаты» | ФСП ID по протоколу OpenID Connect с PKCE, как будет в Keycloak Федерации. Без ФСП человек ничего не теряет. |
| 0:50–1:20 | Кандидат | `jury1@demo.talent` / `demo12345`: опрос (специализация и грейд) → «Тест на грейд» → «Пробный тест», 3–4 задания, видна шкала уверенности → «Прервать». В окне подтверждения сказано, что грейд не меняется и паузы нет. В истории — только этот пробный проход; полный тест (8–20 заданий) запускается с той же страницы | Задание каждый раз новое: ключ от другого экземпляра того же семейства сдаёт 0 %. |
| 1:20–1:50 | Работодатель | «Поиск». На широком экране витрина уже раскрыта: нажать число в ячейке Backend / мидл, не заголовок витрины. В карточке видны грейд, тест и ФСП | Внутри категории выше тот, у кого сильнее тест и ФСП: вклад виден в баллах. |
| 1:50–2:20 | Работодатель | «Потребности» → подсказка «Если поднять верх вилки до …, ожидание закроется ещё у N из M» → «Пригласить» с вилкой до вычета НДФЛ | Подборка учитывает, примет ли человек вилку: оценка двусторонняя. |
| 2:20–2:45 | Кандидат | `fsp001`: «Приглашения» → «Принять» | До принятия имени и контактов нет ни в карточке, ни в ответе API. |
| 2:45–3:00 | Работодатель | Контакты открылись, кнопка «Переписка» | Дальше — переписка на платформе. Проверить самим: `jury1@demo.talent`…`jury10@demo.talent`, пароль `demo12345`. |

Если спросят про точность подбора, говорить так: тест и ФСП упорядочивают людей внутри категории. Спирмен со скрытой силой 0,236 против 0,011 у сортировки по резюме, завышенный грейд в первой десятке 20,1 % против 28,1 %. nDCG@10 полной модели 0,649, у сортировки по резюме 0,620, у строки «без теста и без ФСП» 0,669. Выдача сортируется одной оценкой соответствия. Цифры — `python -m app.validation.matching --check`.

### Ответы, если спросят

Короткие ответы на вопросы, которые жюри задаёт по цифрам. Команды — из каталога `backend/`. Прогон на 300 кандидатах только проверяет пороги и в эти ответы не подставляется.

- Каппа 0,47. Вдали от порога то же решение в 84 % пар, корреляция двух оценок θ — 0,86, взвешенная каппа — 0,58, согласованность по Руднеру — 79,0 %. Команда: `python -m app.validation.assessment --n 2000 --seed 7`.
- Параметры заданий задаёт уровень семейства. В банк пишется априор: средняя ошибка a 0,146 и 0,283. Калибровка по живым ответам — `python -m app.validation.calibrate`.
- Симуляция отвечает по той же модели, которой тест оценивает, поэтому отдельно прогнана ошибка параметров заданий. При σ = 0,30 точность вдали от порога 92,8 %, ложные сдачи 11,6 %. Атака «20 чужих сессий» от модели не зависит: сдача 0,0 % при честной 6,2 %.
- Семейств с вычисляемым ответом семнадцать. На прогоне в 2000 человек другой кандидат видел в среднем 15,2 % заданий. Ключ чужого экземпляра того же семейства сдаёт 0 %.
- Решение с подсказкой модели на MVP не требуется. Есть лимит времени, сигнал несоответствия ответа модели и накопленная сумма по времени и доле верных. Сигнал — повод пересдать, грейд он сам не снимает.
- В тесте на грейд код не запускается: ответ — число, его считает эталон на каждом языке, эталоны гоняет сборка. Задачи с кодом от работодателя выполняются в контейнере `sandbox` без сети и грейд не меняют.
- Цифры воспроизводятся так: `python -m app.validation.assessment --n 2000 --seed 7` и `python -m app.validation.matching --check`. SHA-256 набора подбора на Linux — `c83ce73df96d2f7cc7e1f4bd4b1d1fbf8f661d5fa482cf25b340b65c24100f49`, на Windows — `54a6130ce9b7aa51748ad7f680fbbff39b6f689aadeabed9c313696ea8e76d70`. Цифры этого раздела — с прогона на Linux.
- Сборка: `python -m pytest tests/unit --collect-only -q` собирает 1117 тестов. Последний прогон с покрытием (Python 3.12, все компиляторы, как в CI) напечатал 73,1 % по всему приложению, сервисы 75 %, API 61 %. Порог сборки — 65 %. Интеграционные тесты не проходят, если общее покрытие ниже 72 %, а `pipeline` или `assessment` ниже 60 %. Тестов интерфейса 110, проверок Playwright 67: семь сквозных сценариев и 60 проверок доступности.
- Сорок пользователей — это масштаб из задания. На банке 10 000 профилей и двух процессах API 95-й перцентиль подборки 360 мс, ошибок не было. Команда: `python tests/load_api.py --scenario shortlist --seconds 60 --reuse`.
- Строка «без теста и без ФСП» даёт nDCG@10 0,669, полная модель — 0,649. Польза теста — порядок внутри категории и меньше завышенных грейдов, см. абзац выше. Ярус в этот порядок не вошёл.
- «Завышенный грейд» у нас — показанный грейд выше настоящего: 20,1 % против 28,1 %. Второе определение, настоящий грейд ниже грейда потребности: 19,5 % против 30,9 %. Чужая цифра вроде 4 % посчитана на другом наборе. Оба наших числа печатает `python -m app.validation.matching --check`.
- Метки подбора считаются по скрытой правде, формула видит только заявленное. Слепая каппа оракула на зерне 2027 — 0,46. Разметку двумя людьми процедура умеет считать, файлы пар пока пустые, взвешенную каппу людей не публикуем.
- Проверка подбора вызывает тот же `order_pool`, что и выдача.
- У сервисов есть проверка живости и перезапуск `unless-stopped`; после срока сдачи выкладка заморожена (`DEPLOY_FROZEN`). Адрес стенда: https://89-124-65-102.sslip.io.
- Командное событие весит `1/√n`: так несколько командных явок не перевешивают одну личную победу. Вес одинаков для дисциплин и статусов.
- Клиент OpenID Connect с PKCE готов. Keycloak с демо-реалмом поднимается отдельно и для локального показа не обязателен.
- Строки в PostgreSQL закрыты ролью приложения. На публичном стенде API, worker и beat входят как `fsp_app`. Локальный Compose входит как владелец и переключается на `fsp_app`. Обход чужих идентификаторов: 0 ответов 2xx из 240 запросов. Эпоха токена закрывает старые сессии после смены пароля.
- Работодатель видит витрину и подсказку по вилке и приглашает подходящих, а не разбирает всю ленту откликов.
- Статус «не ищу» убирает человека из поиска. «Открыт к предложениям» снижает вероятность согласия.
- Причина отказа видна в долях рынка, когда в ячейке не меньше пяти человек. После отказа та же компания ждёт 30 дней.
- Доли рынка, четверти зарплат и публичный рейтинг категории считаются только по тем, кого работодатель видит в поиске: одно правило `visible_in_search` (дата рождения, правило для несовершеннолетних, «не ищу», удалённые и приостановленные). Рейтинг категории меньше чем из пяти человек не публикуется.
- Вилка в приглашении подписана «до вычета НДФЛ».
- Регистрация с 15 лет. Для 15–17 лет карточки нет в поиске, пока представитель не подтвердит согласие по ссылке.
- Согласия хранятся с версией текста. Отзыв сразу убирает карточку. В языковую модель уходит только обезличенный текст и только если флаг включён.
- У компании есть метка ИНН, лимит 50 приглашений в день и жалоба. Три разных человека и нижняя граница доли жалоб от 10 % ставят приглашения на паузу до ручной проверки.
- Каждое число в документации повторяется командой. Ключ чужого экземпляра даёт 0 % сдач. Подборка учитывает и соответствие, и вероятность, что человек примет вилку. Жюри проходит тест само: `jury1@demo.talent`…`jury10@demo.talent`, пароль `demo12345`.

### Проверить самим за десять минут

Самопроверка стенда: `make demo-check` (`python -m seed.demo_check`) печатает таблицу «аккаунт → ожидается → факт» по таблице выше и завершается с ошибкой, если хоть один кейс сломан. В `ci.yml` она идёт сразу после сида.

Пароль демо-аккаунтов `demo12345`. На странице входа при включённом демо-режиме есть строка про аккаунты жюри и кнопка «Взять свободный аккаунт жюри». Кнопка берёт ответ `GET /api/v1/public/jury-free`: адрес из `jury1@demo.talent`…`jury10@demo.talent`, в который дольше всех не входили. В ответе только адрес. Если запрос не удался, номер выбирается случайно. Два нажатия до входа могут получить один адрес. Ночной сброс в 04:10 это время входа не очищает. Рядом с «Войти через ФСП ID» написано: демо `FSP001` / `test`.

| Кто | Что сделать | Что увидеть |
|---|---|---|
| `jury1@demo.talent`…`jury10@demo.talent` | Опрос: специализация и грейд обязательны, стаж только подсказывает. «Пробный тест»: до 15 заданий и 5 минут, можно прервать. Затем полный тест, 8–20 заданий | Категория «специализация, грейд». После полного теста грейд подтверждён. У каждого аккаунта жюри свои попытки, паузы между попытками нет |

Регистрацию с нуля можно показать на http://localhost/register. На локальном стенде код подтверждения приходит в Mailpit (http://localhost:8025). На стенде жюри без почтовой учётки код показывается на экране подтверждения, если включены `DEMO_MODE` и `DEMO_SHOW_CODE`. Кандидат 15–17 лет указывает в профиле email представителя. Ссылка уходит письмом. На том же демо-стенде она дополнительно показывается на экране профиля самому участнику и только для адреса, который не кончается на `@demo.talent` или `.demo`. Экран «Забыли пароль?» при `DEMO_MODE` и `MAIL_MODE=console` пишет: «На демо-стенде письма не отправляются, используйте демо-аккаунты». Код сброса на экран не выводится.

Для демо `.env` можно не трогать. Основные параметры:

SOLUTION.md), пусто | YandexGPT вместо GigaChat, если `GIGACHAT_CREDENTIALS` пуст. Основная модель — YandexGPT Pro 5.1. Псевдоним `yandexgpt/latest` — это Pro 5, его не используют. Ключ сервисного аккаунта с ролью `ai.languageModels.user`; запросы уходят с `x-data-logging-enabled: false`. Для черновиков заданий нужна вторая модель, `yandexgpt-5-lite/latest` |

Веса лежат в `models/bge-reranker-v2-m3` и в репозиторий не входят. Устройство: `auto`, `cpu` или `gpu`. Пока режима нет или папки нет, порядок прежний. BM25 — формула без файла весов и в выдачу не входит. Навыки, грейд и нижняя граница ФСП не меняются |

## 11. Развёртывание на сервере

Продуктивная сборка — `deploy/docker-compose.prod.yml`. По ней работает стенд жюри https://89-124-65-102.sslip.io. Отличия от локальной: вход — Caddy 2.10 с автоматическим сертификатом Let's Encrypt вместо nginx, API, worker и beat входят в базу ролью `fsp_app`, Mailpit поднимается только с профилем `mailpit`, добавлен контейнер `backup`. Наружу открыты только 80 и 443 у Caddy. У API, базы и Redis портов на хосте нет.

> Docker-команды раздела сверены с `deploy/docker-compose.prod.yml`, `deploy/caddy/Caddyfile`, `deploy/backup.sh`, `deploy/restore_db.sh` и шагом `deploy` в `.github/workflows/ci.yml`. Именно этими командами обновляется стенд жюри.

### 11.1. Сервер

| Что | Минимум |
|---|---|
| ОС | Linux с Docker Engine 24+ и Compose v2 |
| Процессор и память | 1 vCPU и 4 ГБ. Стенд жюри работает на 8 ГБ, воркер — один процесс |
| Диск | 10 ГБ: образы, база, 14 ночных копий |
| Сеть | Открытые 80 и 443. Без своего домена подходит адрес вида `203-0-113-10.sslip.io`: sslip.io отвечает этим IP на такое имя |
| Почта | SMTP-ящик для кодов подтверждения или профиль `mailpit` для закрытого показа |

Видеокарта не нужна. Образ backend по умолчанию не ставит sentence-transformers и torch (`INSTALL_RERANKER` выключен), `EMBEDDINGS_MODE` и `CROSS_ENCODER_MODE` — `off`.

### 11.2. Первый запуск

```bash
sudo mkdir -p /opt/fsp-talent && sudo chown "$USER" /opt/fsp-talent
git clone https://github.com/KonkovDV/fsp-talent.git /opt/fsp-talent
cd /opt/fsp-talent
cp deploy/.env.example deploy/.env
chmod 600 deploy/.env
openssl rand -hex 32   # SECRET_KEY, APP_DB_PASSWORD
openssl rand -hex 16   # POSTGRES_PASSWORD, SANDBOX_TOKEN
```

Заполните `deploy/.env` (таблица 11.3) и запустите:

```bash
GIT_SHA=$(git rev-parse HEAD) docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env ps
```

При старте backend применяет миграции Alembic от владельца базы, досоздаёт новые таблицы и колонки (`app.core.schema_sync`), выставляет пароль роли `fsp_app` и только потом запускает uvicorn.

Демо-данные загружаются от пользователя `appuser`. Сид от root создаёт ключ подписи удостоверений, который приложение потом не прочитает, и проверка удостоверения отвечает 500.

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec -T -u appuser backend python -m seed.generate_seed
```

Проверка:

```bash
curl -s https://$SITE_ADDRESS/health          # "status":"ok" и "build" — коммит из GIT_SHA
SMOKE_BASE=https://$SITE_ADDRESS/api/v1 SMOKE_MAIL=demo python backend/tests/smoke_api.py
```

Второй командой smoke проверяет стенд снаружи без доступа к почте, если включены `DEMO_MODE` и `DEMO_SHOW_CODE`. Он берёт код из ответа регистрации, проверяет, что `GET /public/issuer` отвечает 200, и пропускает шаги, которым нужны другие письма (сброс пароля, согласие законного представителя). Нужен только Python 3.12, сторонних пакетов скрипт не использует.

### 11.3. Файл `deploy/.env`

Обязательные ключи. Без первых трёх compose не стартует: в файле сборки стоит `${…:?}`.

| Ключ | Что записать |
|---|---|
| `SITE_ADDRESS` | Домен сайта, например `203-0-113-10.sslip.io`. На это имя Caddy получает сертификат |
| `POSTGRES_PASSWORD` | Пароль владельца базы `fsp`: `openssl rand -hex 16` |
| `APP_DB_PASSWORD` | Пароль роли `fsp_app`, под которой работают API, worker и beat: `openssl rand -hex 32`. У роли нет прав суперпользователя, строки закрыты политиками строк |
| `SECRET_KEY` | Ключ подписи токенов: `openssl rand -hex 32`. Если оставить пустым, backend создаст случайный ключ в томе `vc_keys`; на сервере лучше задать явно |
| `SANDBOX_TOKEN` | Общий ключ API и песочницы кода: `openssl rand -hex 16`. Без него sandbox не запускается |
| `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SSL`, `SMTP_USER`, `SMTP_PASSWORD` | Любой SMTP: Яндекс 360, Mail.ru для бизнеса, Unisender Go и другие. `MAIL_MODE=smtp` |

Необязательные ключи:

| Ключ | По умолчанию в примере | Зачем |
|---|---|---|
| `ACME_EMAIL` | пусто | Почта для напоминаний Let's Encrypt об окончании сертификата |
| `FIELD_ENCRYPTION_KEY` | не задан | Отдельный ключ шифрования контактов. Без него шифр берёт `SECRET_KEY` |
| `DEMO_MODE` | true | `true` — аккаунты `jury1@demo.talent`…`jury10@demo.talent`, пробный доступ жюри, демо-провайдер ФСП ID. Для настоящих пользователей `false` |
| `DEMO_SHOW_CODE` | false | Только при `DEMO_MODE=true`: код подтверждения показывается на экране тому, кто регистрируется. Для стенда жюри без почтовой учётки |
| `DEMO_RESET_CRON` | `10 4 * * *` | Ночной возврат стенда жюри к исходному виду, время московское. Пустая строка отключает сброс на время показа |
| `FSP_MODE` | mock | `mock` — демо-реестр протоколов ФСП, `real` — HTTP-клиент по контракту [FSP_INTEGRATION.md](FSP_INTEGRATION.md) |
| `FSP_ID_MODE` | mock | `mock` работает только при `DEMO_MODE=true`. Для настоящих пользователей — `oidc` с `FSP_ID_ISSUER`, `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET` от Keycloak Федерации |
| `AI_ENABLED` и ключи модели | false | Включает языковую модель. Решение принимает оператор: меняется обработка ПДн. Ключи остаются только в `deploy/.env` |

> В `deploy/.env.example` `DEMO_MODE=true` задан один раз, рядом с `DEMO_SHOW_CODE`: пример описывает стенд жюри с демо-провайдером ФСП ID (`FSP_ID_MODE=mock`), а мок без демо-режима backend не запускает. Для настоящих пользователей ставят `DEMO_MODE=false` и `FSP_ID_MODE=oidc`. Если ключ в файле повторяется, compose берёт последнее значение.

`deploy/.env` правит только оператор. Шаг выкладки в CI его не меняет.

### 11.4. HTTPS и Caddy

Конфиг — каталог `deploy/caddy` (`Caddyfile`). Caddy сам получает и продлевает сертификат для `SITE_ADDRESS`, нужен только открытый порт 80 для проверки Let's Encrypt. Он отдаёт статику frontend, проксирует `/api/*`, `/health`, `/docs`, `/openapi.json` и `/.well-known/did.json` на backend и выставляет заголовки: HSTS, CSP, `X-Frame-Options`, `Permissions-Policy` (камера, микрофон и геолокация закрыты). Тело больше 10 МБ получает ответ 413. Пути `/.env` и `/.git` отвечают 404.

Сертификаты лежат в томах `caddy_data` и `caddy_config`. Эти тома при обновлении не удаляют, иначе Caddy заново запросит сертификат и может упереться в лимит Let's Encrypt.

### 11.5. Почта

Есть SMTP-ящик — заполните `SMTP_*` и `MAIL_FROM`. Нет ящика — два варианта:

- закрытый показ: `--profile mailpit` в команде `up`, письма видны в Mailpit на `127.0.0.1:8025` сервера (через SSH-туннель);
- стенд жюри: `DEMO_MODE=true` и `DEMO_SHOW_CODE=true`, код регистрации показывается на экране подтверждения. Код сброса пароля на экран не выводится: «Забыли пароль?» сообщает, что письма со стенда не отправляются.

### 11.6. Резервные копии и восстановление

Контейнер `backup` каждую ночь в 03:30 по часам контейнера (часовой пояс в нём не задан, это UTC — 06:30 МСК) делает `pg_dump -Fc` в `deploy/backups/` и хранит 14 последних файлов с правами `600`.

| Действие | Команда |
|---|---|
| Копия вручную | `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec backup sh /backup.sh` |
| Проверить файл без записи в базу | `python3 deploy/verify_backup.py deploy/backups/fsp_talent-YYYYMMDD-HHMM.dump` |
| Восстановить | см. ниже |

Восстановление заменяет данные в базе. Скрипт сначала проверяет файл тем же `verify_backup.py` и не запускается без `CONFIRM=restore`. Тома Docker он не удаляет.

```bash
CONFIRM=restore ENV_FILE=deploy/.env COMPOSE_FILE=deploy/docker-compose.prod.yml \
  sh deploy/restore_db.sh deploy/backups/fsp_talent-YYYYMMDD-HHMM.dump
```

В дампе есть персональные данные кандидатов: профили, резюме, согласия. Ключ приложения шифрует только часть полей, например контакты. Поэтому копию, которая уходит с сервера, шифруют, а ключ хранят отдельно от неё и от `deploy/.env`. Пример с [age](https://age-encryption.org) (открытый ключ получателя, закрытый на сервере не лежит):

```bash
age -r age1… -o fsp_talent-YYYYMMDD-HHMM.dump.age deploy/backups/fsp_talent-YYYYMMDD-HHMM.dump
# расшифровка на машине с закрытым ключом перед проверкой и восстановлением:
age -d -i key.txt -o fsp_talent-YYYYMMDD-HHMM.dump fsp_talent-YYYYMMDD-HHMM.dump.age
```

То же через GnuPG: `gpg --encrypt --recipient <ключ> файл.dump` (или `gpg --symmetric --cipher-algo AES256 файл.dump` с паролем). `verify_backup.py` и `restore_db.sh` работают с расшифрованным `.dump`. Сам контейнер `backup` пишет файлы без шифрования, с правами `600`, в `deploy/backups/` на сервере. `deploy/.env` с `SECRET_KEY` и `FIELD_ENCRYPTION_KEY` хранят отдельно от копий: без этих ключей контакты из дампа не прочитать.

### 11.7. Обновление

```bash
cd /opt/fsp-talent
docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec backup sh /backup.sh
git pull origin main
GIT_SHA=$(git rev-parse HEAD) docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
curl -s https://$SITE_ADDRESS/health
```

Этими же командами обновляет стенд шаг `deploy` в `.github/workflows/ci.yml`, без ручной копии перед `git pull`. Он запускается после проверок стиля, тестов backend и frontend, сквозного сценария и сборки образов. Если у репозитория стоит переменная `DEPLOY_FROZEN=true` или не задан `DEPLOY_HOST`, шаг пропускается. После срока сдачи `DEPLOY_FROZEN=true` фиксирует код на сервере.

При обновлении не меняются:

- `SECRET_KEY` и `FIELD_ENCRYPTION_KEY` — от них зависит шифр уже записанных контактов;
- том `vc_keys` — в нём ключ подписи удостоверений, без него выданные подписи не проверить;
- тома `postgres_data`, `caddy_data`, `caddy_config`.

Поэтому `down -v` на сервере не выполняют.

### 11.8. Откат

```bash
cd /opt/fsp-talent
git log --oneline -n 10                 # найти предыдущий коммит или тег
git checkout <коммит или тег>
GIT_SHA=$(git rev-parse HEAD) docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env up -d --build
curl -s https://$SITE_ADDRESS/health    # "build" — коммит отката
```

Схема базы при откате кода не возвращается: миграции и `schema_sync` только добавляют таблицы и колонки, предыдущая версия кода с лишними колонками работает. Если выпуск менял сами данные, после отката восстанавливают копию, снятую перед обновлением (раздел 11.6). Вернуться на основную ветку: `git checkout main` и та же команда `up`.

### 11.9. Стенд жюри

- Вернуть показ к исходному виду: `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env exec -T -u appuser backend python -m seed.reset_demo`. После сброса у `jury1@demo.talent`…`jury10@demo.talent` снова пустой опрос, пароль `demo12345`.
- Ночной сброс делает beat по `DEMO_RESET_CRON`.
- Кнопка «Взять свободный аккаунт жюри» на странице входа берёт адрес из `GET /api/v1/public/jury-free`.
- Языковая модель на стенде: оператор вручную задаёт в `deploy/.env` `AI_ENABLED=true`, `YANDEX_MODEL=yandexgpt-5.1/latest`, `YANDEX_CHECK_MODEL=yandexgpt-5-lite/latest`, ключ и каталог, затем выполняет `up -d`.

### 11.10. Вход через ФСП ID

Для настоящих пользователей `FSP_ID_MODE=oidc` и данные клиента Keycloak Федерации. Проверить вход через настоящий OIDC-провайдер можно локально: `docker compose --profile fsp-id up -d` поднимает Keycloak 26.0.7 с демо-реалмом из `deploy/keycloak`, в `.env` ставится `FSP_ID_MODE=oidc`. Без профиля Keycloak не запускается, вход идёт через встроенного демо-провайдера.

## 12. Если что-то пошло не так

| Симптом | Причина и решение |
|---|---|
| `port is already allocated` для 80 | Порт занят другим сервером. Задайте в `.env` `HTTP_PORT=8080` и `PUBLIC_BASE_URL=http://localhost:8080`, затем `make demo` |
| `unknown flag: --wait` | Compose старше 2.17. Обновите Docker Desktop или запустите без флага и подождите минуту: `docker compose up -d --build` |
| `env file .env not found` | Не создан `.env`. Выполните `cp .env.example .env` (Windows: `Copy-Item .env.example .env`) |
| `backend` не становится `healthy` | Посмотрите `docker compose logs backend`. Если там `SECRET_KEY is a published placeholder`, том `vc_keys` недоступен на запись: задайте `SECRET_KEY` в `.env` |
| Вход не работает, `503` | Redis не запущен: `docker compose ps redis`, затем `docker compose up -d redis` |
| Письмо с кодом не пришло | На локальном стенде откройте Mailpit http://localhost:8025. Код можно запросить повторно через минуту. На стенде жюри с `MAIL_MODE=console` письма не уходят: код регистрации показывается на экране, код сброса пароля — нет |
| Проверка удостоверения отвечает 500 | Ключ в томе создан от root. Сид запускают от `appuser` (раздел 11.2). Перезапуск backend отдаёт уже лежащий ключ пользователю `appuser` |
| Caddy не получает сертификат | Порт 80 закрыт или `SITE_ADDRESS` не указывает на этот сервер. Проверьте `docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env logs caddy` |
| `required variable … is missing a value` | В `deploy/.env` не задан `SITE_ADDRESS`, `POSTGRES_PASSWORD` или `APP_DB_PASSWORD` |
| sandbox перезапускается с `SANDBOX_TOKEN is required` | Задайте `SANDBOX_TOKEN` в `deploy/.env` |
| После `git pull` сайт показывает старую версию | Пересоберите образы: `make demo` (или `docker compose up -d --build --wait`) |
| Нужен чистый стенд | `make reset`, затем `make demo` |
| «Вход закрыт на 15 минут после нескольких неверных паролей» у аккаунта жюри | Кто-то пять раз ввёл неверный пароль к этому адресу. Войдите под другим: `jury2@demo.talent`…`jury10@demo.talent` или кнопка «Взять свободный аккаунт жюри» |
| Сборка падает на `npm ci` или `pip install` | Нет доступа к npm или PyPI. Проверьте прокси Docker Desktop (Settings → Resources → Proxies) |
