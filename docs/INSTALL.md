# Сборка, развёртывание и локальный запуск

Инструкция для эксперта, который разворачивает решение на своей машине (ТЗ 3.3, 3.4). Один и тот же путь каждый раз проходит в CI: задание `compose-e2e` выполняет `make demo` и `make check` на чистой машине.

Время первого запуска — 5–10 минут: столько уходит на сборку образов. Повторный запуск занимает меньше минуты.

## 1. Что понадобится

| Что | Версия | Как проверить |
|---|---|---|
| Docker Engine или Docker Desktop | 24 и новее | `docker --version` |
| Docker Compose v2 | 2.17 и новее (нужен флаг `--wait`) | `docker compose version` |
| Git | любая | `git --version` |
| Свободная память | 4 ГБ | всё вместе занимает около 1,5 ГБ |
| Место на диске | 5 ГБ | образы и зависимости |
| Свободные порты | 80 и 8025 | порт 80 можно поменять, см. раздел 9 |

`make` нужен только для коротких команд. В Windows его обычно нет, поэтому для PowerShell рядом даны те же команды без `make`.

Подходит Linux, macOS (Intel и Apple Silicon) и Windows 10/11 с Docker Desktop на WSL 2. Python и Node.js на машине не нужны: всё собирается внутри контейнеров.

На встрече 6 октября машину проверки описали так: около 32–64 ГБ памяти, порядка 8 ядер, без видеокарты. Нашему стенду хватает обычной машины. После срока сдачи смотрят дату коммитов. Идею решения не меняют, упавший контейнер можно поднять снова.

## 2. Получить код

```bash
git clone https://github.com/KonkovDV/fsp-talent.git
cd fsp-talent
```

Если код пришёл архивом, распакуйте его и откройте терминал в папке `fsp-talent`.

## 3. Запустить одной командой

**Linux и macOS**

```bash
make demo
```

**Windows (PowerShell)**

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
docker compose up -d --build --wait
docker compose exec -T -u appuser backend python -m seed.generate_seed
```

`make demo` выполняет те же три шага:

1. Создаёт `.env` из `.env.example`, если файла ещё нет. Править его не нужно. Ключ подписи токенов контейнер сам создаст при первом старте и сохранит в томе `vc_keys`.
2. Собирает образы, поднимает контейнеры и ждёт, пока база, backend, worker, beat и frontend станут `healthy`. Миграции базы применяются при старте backend.
3. Загружает демо-данные. Повторный запуск безопасен: уже загруженное не дублируется.

В конце команда печатает адреса и демо-входы.

## 4. Проверить, что всё работает

| Адрес | Что там |
|---|---|
| http://localhost | Сайт: кабинеты кандидата и работодателя |
| http://localhost/docs | Swagger UI: все методы API с запросами, ответами и кодами ошибок |
| http://localhost/openapi.json | Спецификация OpenAPI 3.1 |
| http://localhost/health | `{"status":"ok",...}` |
| http://localhost:8025 | Mailpit: письма с кодами подтверждения и уведомлениями |

Команда `docker compose ps` должна показать восемь контейнеров в состоянии `running`: nginx, frontend, backend, worker, beat, postgres, redis и mailpit. Проверка здоровья есть у базы, backend, worker, beat и frontend. У redis, Mailpit и nginx её нет. Keycloak стартует отдельно, с профилем `fsp-id`.

Сквозная проверка API на запущенном стенде:

```bash
make check
```

Команда регистрирует нового кандидата (код подтверждения она берёт из Mailpit), привязывает ФСП ID через демо-провайдера, проходит адаптивный тест, ищет кандидата, отправляет приглашение и проверяет раскрытие контактов. Она же проверяет задания от работодателя (с проверкой системой и работодателем), вход через ФСП ID привязанного и нового кандидата, переписку по принятому приглашению и закрытие контактов для одной компании. Она же проверяет аккаунты жюри, согласие законного представителя и обходит все маршруты с идентификатором объекта: другой работодатель и другой кандидат не получают чужих объектов. Успешный прогон заканчивается строкой `SMOKE OK`.

> `make check` меняет демо-данные: например, подтверждает тестом грейд кандидата `fsp001@demo.talent`. Чтобы вернуть стенд к исходному виду, выполните `make reset` и снова `make demo`.

Пароль у всех демо-аккаунтов: `demo12345`. Компании и люди вымышленные.

|---|---|---|

Для привязки ФСП ID в демо-реестре свободны номера FSP2000–FSP2099, пароль `test`. Войти без регистрации можно кнопкой «Войти через ФСП ID» на странице входа: `FSP001` / `test` открывает аккаунт `fsp001@demo.talent`, свободный номер из FSP2000–FSP2099 / `test` создаёт новый аккаунт после экрана согласий.

Пошаговый сценарий из ТЗ — в [README](../README.md#сквозной-сценарий-из-тз-33). Ниже два разных прохода: короткий показ и самостоятельная проверка.

### Показ за три минуты

За десять минут до показа стенд уже поднят (`make demo`). Стенд жюри каждую ночь в 04:10 МСК возвращается в исходное состояние: `make demo-reset`. После сброса у `jury1`…`jury10` снова пустой опрос, поэтому перед показом `jury1` проходит пробный и полный тест на middle по специализации backend. Во второй вкладке вошёл `hr@sibcode.demo`, в третьей — `fsp001@demo.talent`. Пароль у всех `demo12345`. В одной вкладке включена тёмная тема. Если показ сокращают до двух минут, строку 0:20–0:50 пропускают.

| Время | Кто | Что сделать | Что сказать |
|---|---|---|---|
| 0:00–0:20 | — | Слайд «Ответ» | Работодатель находит человека, а не наоборот. Грейд даёт только тест, ФСП — отдельная подтверждённая ось, контакты — после согласия. |
| 0:20–0:50 | Кандидат | Вход → «Войти через ФСП ID» → `FSP001` / `test` → «Результаты» | ФСП ID по протоколу OpenID Connect с PKCE, как будет в Keycloak Федерации. Без ФСП человек ничего не теряет. |
| 0:50–1:20 | Кандидат | `jury1`: «Тест на грейд» → «Пробный тест», 3–4 задания, видна шкала уверенности → «Прервать». В окне подтверждения сказано, что грейд не меняется и паузы нет. В истории полный тест уже подтвердил middle | Задание каждый раз новое: ключ от другого экземпляра того же семейства сдаёт 0 %. |
| 1:20–1:50 | Работодатель | «Поиск». На широком экране витрина уже раскрыта: нажать число в ячейке Backend / мидл, не заголовок витрины. В карточке видны грейд, тест и ФСП | Внутри категории выше тот, у кого сильнее тест и ФСП: вклад виден в баллах. |
| 1:50–2:20 | Работодатель | «Потребности» → подсказка «Если поднять верх вилки до …, ожидание закроется ещё у N из M» → «Пригласить» с вилкой до вычета НДФЛ | Подборка учитывает, примет ли человек вилку: оценка двусторонняя. |
| 2:20–2:45 | Кандидат | `fsp001`: «Приглашения» → «Принять» | До принятия имени и контактов нет ни в карточке, ни в ответе API. |
| 2:45–3:00 | Работодатель | Контакты открылись, кнопка «Переписка» | Дальше — переписка на платформе. Проверить самим: `jury1`…`jury10`, пароль `demo12345`. |

Если спросят про точность подбора, говорить так: тест и ФСП упорядочивают людей внутри категории. Спирмен со скрытой силой 0,240 против 0,011 у сортировки по резюме, завышенный грейд в первой десятке 19,8 % против 28,1 %. nDCG@10 полной модели 0,652, у сортировки по резюме 0,620, у строки «без теста и без ФСП» 0,668. Выдача сортируется одной оценкой соответствия. Цифры — `python -m app.validation.matching --check`.

### Ответы, если спросят

Короткие ответы на вопросы, которые жюри задаёт по цифрам. Команды — из каталога `backend/`. Прогон на 300 кандидатах только проверяет пороги и в эти ответы не подставляется.

- Каппа 0,47. Вдали от порога то же решение в 84 % пар, корреляция двух оценок θ — 0,86, взвешенная каппа — 0,58, согласованность по Руднеру — 79,0 %. Команда: `python -m app.validation.assessment --n 2000 --seed 7`.
- Параметры заданий задаёт уровень семейства. В банк пишется априор: средняя ошибка a 0,146 и 0,283. Калибровка по живым ответам — `python -m app.validation.calibrate`.
- Ответы в симуляции рисует та же модель, которой оцениваем. Поэтому есть прогон с ошибкой параметров. При σ = 0,30 точность вдали от порога 92,8 %, ложные сдачи 11,6 %. Атака «20 чужих сессий» от модели не зависит: сдача 0,0 % при честной 6,2 %.
- Семейств с вычисляемым ответом семнадцать. На прогоне в 2000 человек другой кандидат видел в среднем 15,2 % заданий. Ключ чужого экземпляра того же семейства сдаёт 0 %.
- Решение с подсказкой модели на MVP не требуется. Есть лимит времени, сигнал несоответствия ответа модели и накопленная сумма по времени и доле верных. Сигнал — повод пересдать, грейд он сам не снимает.
- Песочницы с кодом нет: ответ — число, его считает эталон на каждом языке, эталоны гоняет сборка.
- Цифры воспроизводятся так: `python -m app.validation.assessment --n 2000 --seed 7` и `python -m app.validation.matching --check`. Набор подбора имеет SHA-256 `c9a7e21721b8db85aadece223beb76c044928aeff6be46a789ba9df0c9aad552`.
- Сборка: `python -m pytest tests/unit --collect-only -q` собирает 810 тестов. Последний прогон с покрытием напечатал 73,9 % по всему приложению, сервисы 74 %, API 62 %. Порог сборки — 65 %. Интеграционные тесты не проходят, если общее покрытие ниже 72 %, а `pipeline` или `assessment` ниже 60 %. Тестов интерфейса 57, проверок Playwright 67: семь сквозных сценариев и 60 проверок доступности.
- Сорок пользователей — это масштаб из задания. На банке 10 000 профилей и двух процессах API 95-й перцентиль подборки 360 мс, ошибок не было. Команда: `python tests/load_api.py --scenario shortlist --seconds 60 --reuse`.
- Строка «без теста и без ФСП» даёт nDCG@10 0,668, полная модель — 0,652. Польза теста — порядок внутри категории и меньше завышенных грейдов, см. абзац выше. Ярус в этот порядок не вошёл.
- «Завышенный грейд» у нас — показанный грейд выше настоящего: 19,8 % против 28,1 %. Второе определение, настоящий грейд ниже грейда потребности: 19,3 % против 30,9 %. Чужая цифра вроде 4 % посчитана на другом наборе. Оба наших числа печатает `python -m app.validation.matching --check`.
- Метки подбора считаются по скрытой правде, формула видит только заявленное. Слепая каппа оракула на зерне 2027 — 0,46. Разметку двумя людьми процедура умеет считать, файлы пар пока пустые, взвешенную каппу людей не публикуем.
- Проверка подбора вызывает тот же `order_pool`, что и выдача.
- После дедлайна код не меняется. У сервисов есть проверка живости и перезапуск. Адрес стенда в документы попадёт, когда владелец его поднимет.
- Командное событие весит `1/√n`: так несколько командных явок не перевешивают одну личную победу. Вес одинаков для дисциплин и статусов.
- Клиент OpenID Connect с PKCE готов. Keycloak с демо-реалмом поднимается отдельно и для локального показа не обязателен.
- Строки в PostgreSQL закрыты ролью приложения. Обход чужих идентификаторов: 0 ответов 2xx из 124 запросов. Эпоха токена закрывает старые сессии после смены пароля.
- Работодатель видит витрину и подсказку по вилке и приглашает подходящих, а не разбирает всю ленту откликов.
- Статус «не ищу» убирает человека из поиска. «Открыт к предложениям» снижает вероятность согласия.
- Причина отказа видна в долях рынка, когда в ячейке не меньше пяти человек. После отказа та же компания ждёт 30 дней.
- Вилка в приглашении подписана «до вычета НДФЛ».
- Регистрация с 15 лет. Для 15–17 лет карточки нет в поиске, пока представитель не подтвердит согласие по ссылке.
- Согласия хранятся с версией текста. Отзыв сразу убирает карточку. В GigaChat уходит только обезличенный текст и только если флаг включён.
- У компании есть метка ИНН, лимит 50 приглашений в день и жалоба. Три разных человека и нижняя граница доли жалоб от 10 % ставят приглашения на паузу до ручной проверки.
- Каждое число в питче повторяется командой. Ключ чужого экземпляра даёт 0 % сдач. Подборка учитывает и соответствие, и вероятность, что человек примет вилку. Жюри проходит тест само: `jury1`…`jury10`, пароль `demo12345`.

| Кто | Что сделать | Что увидеть |
|---|---|---|

Затем полный тест, 8–20 заданий | Категория «специализация, грейд». После полного теста грейд подтверждён. У каждого `juryN` свои попытки, паузы между попытками нет |

Регистрацию с нуля можно показать на http://localhost/register. На локальном стенде код подтверждения приходит в Mailpit (http://localhost:8025). На стенде жюри без почтовой учётки код показывается на экране подтверждения, если включены `DEMO_MODE` и `DEMO_SHOW_CODE`. Кандидат 15–17 лет указывает в профиле email представителя, и тот подтверждает согласие по ссылке из письма.

## 6. Тесты и проверки

Все команды запускаются на поднятом стенде, внутри контейнера backend.

| Что | Linux, macOS | Windows (PowerShell) |
|---|---|---|
| Юнит-тесты | `make test` | `docker compose exec -T backend python -m pytest tests/unit -q` |
| Стиль кода | `make lint` | `docker compose exec -T backend sh -c "pip install -q ruff==0.16.10 && ruff check app seed tests"` |
| Проверка теста и подбора на синтетике | `make validate` | `docker compose exec -T backend python -m app.validation.assessment --n 300 --seed 7 --check`, затем `docker compose exec -T backend python -m app.validation.matching` |
| Сквозная проверка API | `make check` | `docker compose exec -T -e SMOKE_BASE=http://localhost:8000/api/v1 -e MAILPIT_URL=http://mailpit:8025 backend python tests/smoke_api.py` |
| Нагрузка: 40 пользователей в течение минуты | `make load` | `docker compose exec -T -e SMOKE_BASE=http://localhost:8000/api/v1 -e MAILPIT_URL=http://mailpit:8025 backend python tests/load_api.py` |

Внутри контейнера нет Node.js, Go, Java, Kotlin и .NET, поэтому тесты, которые перезапускают задания на этих языках, пропускаются с пометкой `skipped`. В CI все языки установлены и эти тесты выполняются.

Полные цифры из документации воспроизводятся так:

```bash
docker compose exec -T backend python -m app.validation.assessment --n 2000 --seed 7
docker compose exec -T backend python -m app.validation.matching
docker compose exec -T backend python -m app.validation.matching --seed 7
```

## 7. Остановить, сбросить, обновить

| Действие | Команда |
|---|---|
| Остановить, данные сохраняются | `make down` или `docker compose down` |
| Запустить снова | `make up` или `docker compose up -d --wait` |
| Удалить все данные (база, ключи) | `make reset` или `docker compose down -v` |

| Журнал API | `make logs` или `docker compose logs -f backend` |
| Консоль базы | `docker compose exec postgres psql -U fsp fsp_talent` |

## 8. Что входит в стенд

| Контейнер | Образ | Назначение |
|---|---|---|
| `nginx` | nginx:1.28-alpine | Единая точка входа: сайт, `/api`, `/docs`, заголовки безопасности (CSP) |
| `frontend` | собирается из `frontend/` (node:20 → nginx) | React-приложение для обеих ролей |
| `backend` | собирается из `backend/` (python:3.12-slim) | FastAPI, миграции Alembic при старте, 2 процесса uvicorn |
| `worker` | тот же образ | Celery: пересчёт профилей, истечение приглашений, задача недели, удаление данных по 152-ФЗ |
| `beat` | тот же образ | Расписание задач Celery |
| `postgres` | pgvector/pgvector:pg16 | PostgreSQL 16 с pgvector и pg_trgm |
| `redis` | redis:7.2-alpine | Лимиты запросов, состояние входа через ФСП ID, брокер Celery |
| `mailpit` | axllent/mailpit | Почтовый ящик для писем на локальном стенде |

Наружу открыт только порт nginx. API (8010), отдельный frontend (3010) и Mailpit (8025) слушают только 127.0.0.1. У базы и Redis портов на хосте нет.

## 9. Настройки `.env`

Для демо `.env` можно не трогать. Основные параметры:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `SECRET_KEY` | заглушка | Ключ подписи токенов. Заглушку контейнер заменит случайным ключом. На публичном стенде задайте свой: `openssl rand -hex 32` |
| `HTTP_PORT` | 80 | Порт сайта на хосте. Если 80 занят: `HTTP_PORT=8080` и `PUBLIC_BASE_URL=http://localhost:8080` |
| `PUBLIC_BASE_URL` | http://localhost | Адрес, из которого строятся ссылки в письмах |
| `FSP_MODE` | mock | `mock` — тестовый реестр ФСП, `real` — HTTP-клиент по контракту из [FSP_INTEGRATION.md](FSP_INTEGRATION.md) |
| `FSP_ID_MODE` | mock | `mock` — демо-страница провайдера, `oidc` — Keycloak Федерации (`FSP_ID_ISSUER`, `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET`) |
| `AI_ENABLED`, `GIGACHAT_CREDENTIALS` | true, пусто | Без ключа GigaChat резюме разбирается правилами. С ключом модель только добавляет навыки с дословной цитатой |
| `EMBEDDINGS_MODE` | off | `model` включает смысловой поиск по эмбеддингам. Нужны зависимости `.[ai]` (sentence-transformers и torch), в демо-образ они не входят |
| `MAIL_MODE`, `SMTP_*` | smtp → Mailpit | Настоящий SMTP на стенде |

## 10. Запуск без Docker (для разработки)

Нужны Python 3.12, Node.js 20+, PostgreSQL 16 с расширением pgvector и Redis 7.

```bash
# backend
cd backend
python -m venv .venv && source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -c requirements.lock -e ".[test]"
export DATABASE_URL=postgresql+asyncpg://fsp:fsp@localhost:5432/fsp_talent
export REDIS_URL=redis://localhost:6379/0
export SECRET_KEY=$(python -c "import secrets; print(secrets.token_hex(32))")
export MAIL_MODE=console VC_PRIVATE_KEY_PATH=./vc_ed25519.pem
alembic upgrade head
python -m seed.generate_seed
uvicorn app.main:app --reload --port 8000

# frontend, в другом терминале
cd frontend
npm ci
npm run dev        # http://localhost:5173, запросы /api уходят на :8000
```

Коды подтверждения при `MAIL_MODE=console` печатаются в журнал uvicorn.

## 11. Публичный стенд с HTTPS

Продовая сборка (`deploy/docker-compose.prod.yml`) использует Caddy с автоматическим сертификатом Let's Encrypt и ночные резервные копии базы. Домен покупать не нужно: подходит адрес вида `203-0-113-10.sslip.io`. Шаги описаны в [deploy/README.md](../deploy/README.md).

В продовой сборке есть те же worker и beat, что и локально: задача недели, истечение приглашений, синхронизация с ФСП и, при `DEMO_MODE=true`, ночной возврат стенда жюри в 04:10 МСК (`make demo-reset`). Письма уходят на SMTP из `deploy/.env` (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`); без своего почтового сервера стенд поднимается с `--profile mailpit`, и письма видны в Mailpit на 127.0.0.1:8025 сервера. Режим жюри включается `DEMO_MODE=true`, для настоящих пользователей он выключен.

Если почтовой учётки для стенда жюри нет, в `deploy/.env` ставятся `DEMO_MODE=true` и `DEMO_SHOW_CODE=true`: после регистрации экран подтверждения показывает код плашкой «Демо-стенд: письма отсюда не уходят», код видит только тот, кто регистрируется. Без `DEMO_MODE` вторая настройка не действует. Проверка стенда снаружи без доступа к почте:

```bash
SMOKE_BASE=https://<адрес стенда>/api/v1 SMOKE_MAIL=demo python backend/tests/smoke_api.py
```

В этом режиме smoke берёт код из ответа регистрации и пропускает шаги, которым нужны другие письма (сброс пароля, согласие законного представителя).

Выкладка на сервер запускается только после зелёных проверок стиля, тестов backend и frontend, сквозного сценария и сборки образов. После дедлайна владелец ставит переменную репозитория `DEPLOY_FROZEN=true`: выкладка пропускается, даже если проверка зелёная.

Презентация `docs/pitch.pdf` сохраняется из `docs/pitch.pptx` средствами PowerPoint («Сохранить как → PDF»): в файле обязательные слайды шаблона ЛЦТ, и сборщик PDF из HTML их не повторяет.

Проверка входа через настоящий OIDC-провайдер локально: `docker compose --profile fsp-id up -d` поднимает Keycloak с демо-реалмом из `deploy/keycloak`, в `.env` ставится `FSP_ID_MODE=oidc`. Без профиля Keycloak не запускается, вход идёт через встроенного демо-провайдера.

## 12. Если что-то пошло не так

| Симптом | Причина и решение |
|---|---|
| `port is already allocated` для 80 | Порт занят другим сервером. Задайте в `.env` `HTTP_PORT=8080` и `PUBLIC_BASE_URL=http://localhost:8080`, затем `make demo` |
| `unknown flag: --wait` | Compose старше 2.17. Обновите Docker Desktop или запустите без флага и подождите минуту: `docker compose up -d --build` |
| `env file .env not found` | Не создан `.env`. Выполните `cp .env.example .env` (Windows: `Copy-Item .env.example .env`) |
| `backend` не становится `healthy` | Посмотрите `docker compose logs backend`. Если там `SECRET_KEY is a published placeholder`, том `vc_keys` недоступен на запись: задайте `SECRET_KEY` в `.env` |
| Вход не работает, `503` | Redis не запущен: `docker compose ps redis`, затем `docker compose up -d redis` |
| Письмо с кодом не пришло | Откройте Mailpit http://localhost:8025. Код можно запросить повторно через минуту |
| После `git pull` сайт показывает старую версию | Пересоберите образы: `make demo` (или `docker compose up -d --build --wait`) |
| Нужен чистый стенд | `make reset`, затем `make demo` |
| Сборка падает на `npm ci` или `pip install` | Нет доступа к npm или PyPI. Проверьте прокси Docker Desktop (Settings → Resources → Proxies) |
